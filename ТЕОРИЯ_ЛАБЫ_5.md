## Что здесь особенно важно для защиты

Пятая лабораторная меняет место, где появляется первый интерфейс. В четвертой браузер получал приложение Vue и сам запрашивал данные. В пятой Nuxt должен уметь получить данные заранее и вернуть HTML с содержимым. При этом Java сохраняет проверку паролей, выпуск токенов, права и работу с PostgreSQL. Главный теоретический вопрос всей работы: как связать серверный HTML, состояние браузера и ответы Java с нужным пользователем и корректно обновлять данные после изменений.

В этом тексте есть три основания для выбора тем. **Письменная программа защиты** — пятнадцать вопросов на второй странице `Лабораторная 5.pdf`. Все они включены, даже если соответствующий механизм не используется в коде. **Материал лекций** — прежде всего `Лекция№10.pdf`, а также связанные темы SPA и Vue из лекций 8 и 9. **Вероятные уточнения Минтуса** — предположение по сообщениям Карима о предыдущих защитах и замечаниях к работе. Они не являются обещанием, что преподаватель задаст именно эти вопросы.

По этим сообщениям особенно важно объяснять причинную связь, а не только расшифровывать сокращение. Для SSR недостаточно сказать «рендеринг на сервере»: нужно провести запрос от URL до HTML и объяснить последующую гидратацию. Для кеша недостаточно сказать «храним тридцать секунд»: нужно назвать ключ, пользователя, момент устаревания и способ удаления результата. Для middleware недостаточно показать условие `if`: нужно объяснить, кто реально запрещает изменение записи, если клиентский интерфейс обойти.

Поэтому самые подробные места — следующие:

- **SSR и браузерное выполнение:** что выполняется дважды, что передается через payload, почему `window` недоступен серверу и откуда берутся cookies.
- **Загрузка и свежесть данных:** зачем `useAsyncData`, где возникают лишние последовательные ожидания и почему один общий кеш может показать чужие данные.
- **Доступ и состояние:** почему Java остается источником решения о правах, а Pinia и middleware обеспечивают согласованный интерфейс.
- **Поведение после изменений:** зачем нужны инвалидация, уведомление и повторное чтение, чем они отличаются и почему ручной SQL тоже должен учитываться.

Отдельные абзацы «Возможное уточнение на защите» развивают уже объясненный механизм. Они показывают, где простой ответ требует следующего шага рассуждения. Это не дополнительные требования к реализации и не дословные вопросы преподавателя. Разбор относится к текущему Nuxt-варианту lab5; при сравнении с другими метафреймворками их API не переносится в Nuxt по сходству названий.

Теория связана с исходниками короткими примерами. Полный построчный разбор не дублируется: для него есть отдельный `РАЗБОР_ДЛЯ_ДАНИЛА.md`. Здесь важнее понимать, какую проблему решает механизм, где заканчиваются его гарантии и как обосновать выбор для этой лабораторной.

## Зачем после Vue понадобился Nuxt

### Какую проблему решает метафреймворк

В четвертой лабораторной Vue уже умел строить список, реагировать на ввод и менять карточку после получения данных. Однако при прямом открытии адреса браузеру сначала приходилось получить приложение, выполнить JavaScript и лишь затем собрать содержимое. Пятая лабораторная требует другого первого ответа: сервер должен подготовить HTML с данными выбранной страницы. Появляются новые вопросы: кто обработает URL, где получить данные до рендеринга, как передать их браузеру и как продолжить работу без потери состояния.

Метафреймворк объединяет решения этих задач вокруг выбранной технологии интерфейса. В нашем варианте Vue описывает компоненты и их реактивное поведение, а Nuxt организует приложение: файловые маршруты, серверный рендеринг, загрузку данных, плагины, middleware и передачу начального состояния. Здесь полезно различать уровни. Vue отвечает за компонент и его отображение. Nuxt знает, как получить из URL целую страницу и как связать серверный этап с браузерным.

Из этого не следует, что Vue сам по себе принципиально не способен на SSR. У Vue есть серверный renderer. Но если брать его напрямую, придется самостоятельно согласовывать маршрутизатор, получение данных, серверное состояние, клиентские ресурсы и гидратацию. Nuxt предоставляет готовую организацию такой работы. Смысл его использования в лабораторной именно в этом, а не в замене расширения файлов или новом названии папки.

В лекции 10, на слайдах 26–29, метафреймворк показан как расширение UI-фреймворка. Это подходящий ответ на вопрос о различии технологий: React, Vue, Svelte и Angular задают основу интерфейса; соответствующие метафреймворки добавляют соглашения для приложения и разных режимов его выполнения.

| Основа интерфейса | Метафреймворк из ТЗ | На чем сосредоточиться в сравнении |
| --- | --- | --- |
| React | Next.js | Файловые маршруты, серверная загрузка, SSR; в App Router также разделение Server и Client Components |
| Vue | Nuxt | Vue-компоненты, composables Nuxt, сервер Nitro и согласованная передача данных при SSR |
| Svelte | SvelteKit | Организация приложения вокруг Svelte, маршруты, загрузка данных и выбор режима рендеринга |
| Angular | AnalogJS | Метафреймворк вокруг Angular с файловыми маршрутами, SSR и статической генерацией |

Таблица не означает одинаковых API. Файл `page.jsx` из Next.js не является названием страницы Nuxt, а React Server Components нельзя автоматически приписать Vue. Общие проблемы похожи, конкретные механизмы отличаются. Для защиты варианта Nuxt нужна уверенная модель своей реализации и понимание назначения остальных вариантов, без попытки пересказать каждую их функцию. Сопоставление экосистем дано и в лекции 10, слайд 28; особенности подтверждают официальные документы [Next.js](https://nextjs.org/docs/app/getting-started/server-and-client-components), [SvelteKit](https://svelte.dev/docs/kit/introduction) и [AnalogJS](https://analogjs.org/docs).

### Почему сервер Nuxt не заменяет Java-backend

Слово «сервер» описывает место выполнения кода, но еще не объясняет его обязанности. Java в нашем приложении проверяет учетные данные и права, выполняет операции над студентами и обращается к PostgreSQL. Nuxt получает разрешенные данные через HTTP и строит пользовательскую страницу. Оба процесса находятся на серверной стороне, однако решают разные задачи.

Это прямо связано с ограничением ТЗ: бизнес-логика, авторизация и БД остаются на Java-backend. Поэтому наличие серверного JavaScript не дает основания перенести туда проверку паролей или запросы jOOQ. Серверный код Nuxt здесь обслуживает frontend: узнает пользователя для SSR, получает данные и формирует HTML. Проверка маршрута в Nuxt помогает выбрать страницу; окончательное решение по API остается у Java.

Возможное уточнение на защите: **«Если Nuxt уже умеет серверные endpoint, зачем Java?»** В общем проекте архитектура могла бы быть иной. В этой лабораторной Java является источником бизнес-правил и данных по условию задания, а сервер Nuxt нужен для подготовки интерфейса. Два процесса не дублируют один backend: один реализует предметные операции, другой использует их при рендеринге страницы.

## Как страница появляется: MPA, SPA, CSR и SSR

### Навигация и рендеринг отвечают на разные вопросы

MPA, multi-page application, означает приложение с переходами через получение новых HTML-документов. Браузер запрашивает одну страницу, затем при обычном переходе запрашивает другую. SPA, single-page application, сохраняет один загруженный документ и меняет его содержимое средствами JavaScript. При этом у SPA могут быть разные URL, история переходов и много отдельных компонентов. «Single page» не означает один адрес или один экран.

CSR и SSR классифицируют другую сторону работы: где строится содержимое страницы. CSR, client-side rendering, создает его в браузере. SSR, server-side rendering, подготавливает HTML на сервере. Поэтому фраза «у нас SSR, значит это больше не приложение с клиентской навигацией» неверна. В Nuxt первоначальный документ может появиться через SSR, а следующие переходы выполняться внутри уже работающего браузерного приложения.

Это различие видно на адресе `/students/17`. При прямом открытии браузер просит документ у сервера Nuxt. При нажатии внутреннего `<NuxtLink>` маршрутизатор может загрузить нужные ресурсы и данные, а затем сменить страницу без нового документа целиком. URL одинаков, но точка начала работы разная. В лекции 10 эта связь разобрана на слайдах 4–6 и 35.

Ощущение быстрых переходов у SPA объясняется сохранением общей оболочки и загруженного JavaScript. Не требуется заново получать все ресурсы при каждом действии. Обратная сторона проявляется на первом экране: если еще нет кода приложения и данных API, содержимое появляется позже. Удаление полного перехода не удаляет сетевые задержки; они переходят в другие запросы.

### Что происходит при CSR

Представим прямое открытие карточки в приложении с чистым CSR. Сервер отдает HTML-оболочку и ссылки на ресурсы. Браузер получает JavaScript, разбирает его и создает приложение. Маршрутизатор определяет карточку, после чего начинается получение данных студента. Лишь получив ответ, Vue может построить содержимое карточки. Часть ресурсов может приходить параллельно, но зависимость «нужен работающий код, чтобы начать конкретное чтение» способна задерживать первый экран.

Преимущества CSR связаны с распределением работы. Статическую оболочку и ресурсы удобно раздавать, а построением интерфейса занимается устройство пользователя. Для внутреннего интерфейса с большим количеством действий это может быть разумным выбором. Но слабое устройство тратит больше времени на JavaScript, а плохая сеть усиливает цену цепочки запросов. Дополнительно приходится учитывать, какое содержимое доступно поисковым роботам и другим клиентам, которые не выполняют приложение так же, как обычный браузер.

Фраза «SPA не индексируется» слишком категорична: разные роботы имеют разные возможности. Практическая проблема состоит в зависимости содержимого от выполнения JavaScript и дополнительных запросов. SSR и SSG позволяют получить основные сведения прямо в HTML. Но для закрытой страницы студентов поисковая индексация сама по себе не является целью: такие сведения вообще не должны становиться общедоступными ради SEO.

### Что переносится на сервер при SSR

При SSR сервер Nuxt получает URL, выбирает маршрут, создает приложение для запроса и выясняет необходимые данные. В нашей карточке начальная загрузка связана с `useAsyncData`, а обращение к студенту выполняется через `$students`. Java возвращает данные, после чего Vue на сервере превращает состояние страницы в HTML. Браузер получает уже содержательную карточку, а не только место, куда ее когда-нибудь добавит клиентский код.

Такой путь не означает, что Nuxt непосредственно читает таблицу студентов. Между renderer и БД остается Java API. Также SSR не означает, что пользовательский JavaScript больше не нужен. Сервер не отправляет браузеру живой объект Vue: он передает HTML, данные и ссылки на клиентский код. Браузер затем создает собственное приложение и связывает его с разметкой. Этот следующий этап называется гидратацией.

В [nuxt.config.js](frontend/nuxt.config.js) указано `ssr: true`, а серверный preset — `node-server`. Но одной настройки мало, чтобы начальные данные действительно оказались в HTML. Если все полезное чтение перенести в `onMounted`, оно произойдет только в браузере. Сервер сможет построить лишь ту часть интерфейса, для которой у него уже есть состояние. Настоящий SSR данных требует их получения до завершения серверного рендеринга.

Возможное уточнение на защите: **«Почему нельзя просто включить `ssr: true` и оставить загрузку в `onMounted`?»** Потому что mounted-хук не является этапом SSR. Сервер не монтирует компонент в браузерный DOM. Данные, полученные только в этом хуке, не участвуют в первоначальном серверном HTML. В lab5 первая загрузка карточки поэтому выполняется через `useAsyncData`; mounted-этап нужен для последующего браузерного поведения.

### Где SSR помогает и за что приходится платить

SSR уменьшает зависимость первого содержимого от полного выполнения клиентского JavaScript. Это особенно заметно, если устройство медленно обрабатывает большой клиентский код. Но перед отправкой содержательного HTML серверу самому требуется получить данные и выполнить рендеринг. Медленный Java API может задержать весь этот ответ.

TTFB, time to first byte, описывает время до первого байта ответа. В него входят сеть и ожидание серверной работы, а не только вычисление шаблона. У SSR TTFB способен вырасти по сравнению с быстро отданной статической оболочкой CSR. При этом содержательный экран все равно может появиться раньше, потому что после ответа не требуется заново проходить всю клиентскую цепочку получения данных. Одна метрика не заменяет весь пользовательский результат.

В лекции 10, слайды 12–15, прямо сопоставлены эти издержки. Плохой ответ на защите — «SSR всегда быстрее». Более точный: SSR меняет порядок работы и часто ускоряет появление содержимого, но добавляет серверную нагрузку и зависит от времени получения данных. Если тормозит БД, выбор места рендеринга не исправляет запрос к ней автоматически.

Есть и организационная цена. Нужна среда, которая выполняет серверное приложение, а код должен учитывать два окружения и изоляцию пользователей. Статический сервер с одним набором файлов больше не выполняет все необходимые обязанности. Поэтому выбор SSR — обоснованный компромисс, а в нашей лабораторной еще и прямое требование задания, а не универсальное улучшение любого сайта.

### Как отличить серверное содержимое от результата клиентской работы

Готовая карточка на экране сама по себе еще не доказывает SSR: при CSR браузер тоже в итоге построит такую карточку. Инспектор элементов показывает текущий DOM, который уже мог изменить JavaScript. Для различения подходов важно содержимое первоначального HTML-ответа на запрос документа. Если нужные имя и поля пришли там, они подготовлены до клиентского отображения. Если в ответе находится только оболочка, а поля появились после API-запроса браузера, наблюдается другой путь.

При этом данные в отдельном payload и уже построенная HTML-разметка — не одно и то же доказательство. Сервер мог отправить JSON, оставив создание видимой карточки клиенту. Требование SSR данных проверяют по содержательному HTML выбранной страницы. Ошибочно также искать в ответе обязательно все данные приложения: сервер подготавливает конкретный маршрут и необходимый ему первый экран, а не заранее рендерит все возможные страницы.

Возможное уточнение на защите: **«Если JavaScript отключен, SSR продолжает существовать?»** Да, уже полученное серверное содержимое может быть показано. Но интерактивное поведение, зависящее от Vue, не подключится. Поэтому видимая карточка и работающий обработчик удаления служат свидетельствами разных этапов. Успешный SSR не означает, что весь функционал приложения обязан работать без JavaScript.

## Стратегии рендеринга и выбор между свежестью и готовым ответом

### SSG: подготовить HTML заранее

SSG, static site generation, строит HTML заранее, обычно во время подготовки версии сайта. Когда посетитель запрашивает страницу, сервер или CDN отдает готовый результат. CDN, content delivery network, — сеть узлов для доставки содержимого ближе к пользователю. Ее наличие не является обязательным условием SSG, но хорошо сочетается с раздачей общих статических страниц.

Главное достоинство — получение документа не требует заново выполнять весь рендеринг для каждого посетителя. Подход удобен для документации, справочных страниц или редко меняющихся публичных материалов. Главное ограничение связано с актуальностью: сохраненный HTML отражает данные, доступные в момент генерации. Если содержание поменялось, прежняя страница сама по себе не узнает об этом.

Статически подготовленная страница может содержать клиентский JavaScript, гидратироваться и затем читать новые данные. «Статическая» описывает способ получения начального HTML, а не запрет на любые действия после его получения. Но если персональные данные появляются только из позднего браузерного запроса, они не становятся персональным SSR от одного наличия заранее созданной оболочки.

Для защищенного профиля SSG не заменяет SSR. Во время общей генерации еще неизвестно, чей именно браузер позже откроет `/profile`. Если сохранить в одной общедоступной версии профиль конкретного человека, возникнет утечка. Можно заранее подготовить неперсональную оболочку и позже получать пользователя, однако это другая стратегия первого экрана. В lab5 профиль строится по текущему запросу, а SSG для него не используется.

### ISR: обновлять отдельные готовые страницы

ISR, incremental static regeneration, сочетает повторное использование готовой страницы с ее последующим обновлением. Не требуется заново готовить весь сайт ради каждой изменившейся карточки каталога. Система сохраняет страницы и по предусмотренному правилу пересоздает нужные результаты. Точное поведение зависит от метафреймворка, конфигурации и среды размещения.

Важный вопрос здесь звучит не «есть ли кеш», а «когда сохраненный результат перестает считаться достаточно свежим и что получит посетитель во время обновления». Возможны разные правила ожидания. Например, при устаревании система может выдать прежнюю страницу и параллельно подготовить следующую. Следующий запрос после удачного обновления уже получит новую версию. Именно такой сценарий изображен в лекции 10, слайды 18–19.

Из него не следует, что каждые заданные десять секунд сервер обязательно сам начинает фоновую работу. В распространенной схеме срок определяет свежесть, а проверку и обновление инициирует обращение. Также первый посетитель после истечения срока не обязательно получает уже новую версию: он может увидеть старую, ставшую причиной фонового обновления. На защите важно проговорить выбранное правило, а не обещать «всегда свежую статику».

### ISR и SWR — разные понятия

SWR, stale-while-revalidate, описывает поведение кеша: временно вернуть имеющуюся устаревшую копию, пока выполняется проверка или обновление. Это применимо не только к HTML, но и к данным API. ISR описывает механизм обновления сохраненных страниц. Эти понятия часто встречаются вместе, но не являются полными синонимами.

Рассмотрим три обращения к публичному каталогу. Первое получает сохраненную свежую версию. Ко второму срок свежести уже прошел; оно получает старую копию и инициирует обновление. Третье приходит после успешного обновления и получает новую. Это удобный пример SWR-поведения, которым может пользоваться механизм регенерации страниц. Однако при ошибке обновления новая версия не возникает чудесным образом: дальнейшее поведение определяется политикой кеша.

В Nuxt режимы рендеринга и правила для маршрутов описаны в [официальной документации](https://nuxt.com/docs/4.x/guide/concepts/rendering). Для нашей защиты достаточно понимать назначение таких правил и их ограничения. В текущем `nuxt.config.js` нет правил `swr` или `isr` для страниц студентов. Собственный кеш объектов студентов не превращает приложение в ISR: он сохраняет данные, а не автоматически регенерирует статические HTML-страницы.

### Гибридный рендеринг

Слово «гибридный» употребляют в двух близких контекстах. Первый — приложение сочетает серверный первый HTML и последующую клиентскую работу. Второй, на котором сосредоточен слайд 24 лекции 10, — разные маршруты одного сайта получают разные стратегии: справка через SSG, личный кабинет через SSR, отдельный интерактивный экран через CSR. Нельзя незаметно подменять одно значение другим.

Nuxt позволяет управлять поведением маршрутов через route rules, но сам факт использования Nuxt не доказывает, что разработчик настроил все режимы сразу. В lab5 серверный рендеринг включен для приложения, после него работает клиентская навигация; раздача персональных страниц через общий ISR-кеш не настроена. Это точное описание выполненной работы без добавления функций, которых в исходниках нет.

Выбор стратегии удобно начинать с требований страницы. Если сведения одинаковы для всех и редко меняются, заранее подготовленный HTML может быть достаточен. Если они часто меняются, нужно определить допустимое устаревание. Если результат персональный, необходимо учитывать пользователя и границы кеша. Если экран состоит в основном из действий уже вошедшего человека, CSR может быть практичным, хотя в конкретной лабораторной SSR обязателен.

Возможное уточнение на защите: **«Почему не включить ISR на все страницы и получить сразу скорость и свежесть?»** Потому что сохраненная страница имеет ключ и срок жизни. Общий ключ способен смешать персональные результаты, а фоновой проверке свойственно окно устаревания. Режим выбирают по допустимому поведению конкретной страницы. Стратегия рендеринга не отменяет проверку доступа и не делает общую копию безопасной для разных пользователей.

## Гидратация: почему одинаковый экран строится в двух окружениях

### HTML, видимое содержимое и работающие обработчики

Когда сервер вернул HTML, браузер еще не обязательно закончил всю работу. Он должен разобрать разметку, получить нужные стили, отобразить содержимое и выполнить клиентский код. Поэтому полезно различать три момента: документ получен, нужное содержимое стало видно, интерфейс готов обрабатывать действия средствами приложения. Они не обязаны совпадать. Это центральная мысль лекции 10, слайды 39–41.

Гидратация связывает существующий серверный HTML с клиентским приложением. Vue создает клиентские экземпляры компонентов, восстанавливает необходимое состояние и подключает обработчики. Уже показанная разметка используется как начальный результат, а не обязательно уничтожается ради полного создания заново. После этого изменение реактивного состояния может обновлять DOM обычным образом.

Например, серверная карточка уже показывает имя студента. Браузеру не требуется сначала получить пустую карточку и самостоятельно узнать то же имя только ради первого отображения. Но работа обработчика кнопки удаления зависит от клиентского приложения. Само наличие элемента `<button>` в HTML не означает, что JavaScript-обработчик Vue уже подключен. При этом обычная ссылка и другие нативные возможности HTML могут действовать и без гидратации: нельзя распространять зависимость конкретной кнопки на все элементы страницы.

Гидратация также не означает повторное обращение за HTML-документом. Сеть может понадобиться для JavaScript и других ресурсов, однако задача отличается от новой навигации. И она не требует повторно запрашивать все данные API. В lab5 начальные результаты `useAsyncData` и состояние Pinia передаются браузеру, поэтому первый клиентский рендер может опираться на серверные сведения.

### Два выполнения кода не означают общую память

При универсальном рендеринге код обычной страницы участвует в создании серверного компонента, а затем клиентского. Это разные исполнения и разные объекты. Серверный `ref` не перемещается по сети как живая ссылка; передается сериализуемое состояние. Если позже в браузере изменится поле формы, серверный объект не изменится от самого этого присваивания.

По той же причине начальную функцию компонента нельзя понимать как место, которое гарантированно выполняется только на компьютере пользователя. Создание локального состояния обычно допустимо в обеих средах. Обращение к `window`, `document` и `localStorage` требует браузерной среды. На сервере существуют другие возможности, например доступ к HTTP-запросу и приватной конфигурации.

В lab5 [01.session.js](frontend/app/plugins/01.session.js) отделяет эти ветви через `import.meta.client` и `import.meta.server`. Браузерная ветка работает с Web Locks и событиями окна; серверная переносит Cookie и Set-Cookie. Это не разные версии бизнес-авторизации: Java по-прежнему проверяет учетные данные, а frontend использует подходящий для среды способ обращения.

Ошибка окружения и mismatch тоже не являются синонимами. Если сервер дошел до обращения к отсутствующему `window` и получил исключение, нормальный HTML мог вообще не сформироваться: это ошибка серверного выполнения. Если же сервер успешно показал одну ветку интерфейса, а клиент при первом рендере ожидает другую, возникает расхождение гидратации. Внешне оба случая могут выглядеть как «страница неправильно открылась», но причины и исправления отличаются.

Само объявление функции с браузерным кодом еще не означает, что ее тело выполнилось на сервере. Важно место вызова. Например, обработчик пользовательского щелчка обычно вызывается в браузере, хотя описывающий его модуль участвовал в SSR. А подписка на глобальное событие, созданная непосредственно при серверном выполнении, уже является побочным действием. Нужно отличать описание дальнейшего поведения от его немедленного выполнения.

### Что именно расходится при hydration mismatch

Hydration mismatch возникает, когда DOM, полученный из серверной разметки, не соответствует тому начальному результату, который ожидает клиентский renderer. Это не любое последующее изменение интерфейса. После завершения гидратации нормальное обновление времени или списка не является ошибкой само по себе. Проблема касается согласования первоначального результата.

Простейший источник — `Math.random()` непосредственно в отображаемом выражении. Сервер получил одно значение, браузер вычислил другое. Похожая ситуация возникает с текущим временем: между двумя исполнениями проходит время, а часовые пояса могут различаться. Еще один источник — повторное чтение изменившихся данных без использования начального серверного результата. Сервер показал одно имя, клиент еще до согласования ожидает уже другой ответ.

Не все причины находятся в данных. Некорректная HTML-вложенность может быть исправлена самим браузером при разборе документа. Тогда фактический DOM отличается от структуры, ожидаемой Vue. Возможна и зависимость первой разметки от ширины окна: сервер не знает реальный размер экрана, а браузер выбирает другую ветку. Поэтому сначала устанавливают конкретный источник различия, а не скрывают предупреждение.

Исправление выбирают по смыслу значения. Данные первого экрана следует передать из SSR в браузер. Для случайного начального значения можно сохранить результат в SSR-совместимом состоянии, вместо независимого вычисления в каждой среде. Чисто браузерные сведения можно получать после монтирования. Адаптивное оформление часто лучше выразить CSS media queries: тогда исходная структура остается согласованной и браузер сам применяет нужные стили.

Возможное уточнение на защите: **«Если поставить весь экран внутрь `ClientOnly`, mismatch исчезнет?»** Для исключенной из SSR части можно убрать саму необходимость такого сопоставления, но содержимое перестанет участвовать в первоначальном серверном HTML. Это допустимо для действительно браузерного виджета, однако не выполняет задачу SSR защищенной карточки. Исправлять случайное различие данных полным отказом от серверного содержимого обычно означает обходить причину.

### Почему недостаточно убрать предупреждение

Renderer способен восстанавливаться после некоторых расхождений, но такое восстановление может потребовать дополнительной работы и замены узлов. Пользователь способен увидеть скачок содержимого, а состояние интерфейса становится труднее объяснить. Отсутствие заметного сбоя при одном открытии еще не доказывает правильность первоначальных состояний.

Лектор на слайде 43 прямо предлагает искать причину расхождения. В нашей реализации особенно чувствительны сведения о пользователе: сервер и браузер должны начать с согласованного состояния, иначе шапка и защищенная страница могут ожидать разную картину входа. Отдельная задача — получить свежие сведения позже, когда сессия действительно изменилась. Ее не следует смешивать с первым рендером.

Практическое правило для объяснения любой строки здесь такое: определить среду, время вызова и данные первого отображения. Тогда становится понятно, почему `onMounted` подходит для подписки браузера, но не заменяет начальное получение карточки, а SSR-payload помогает согласовать два исполнения. Дополнительные причины и способы исправления перечислены в [документации Nuxt о гидратации](https://nuxt.com/docs/4.x/guide/best-practices/hydration).

Согласованный первый экран не обязан оставаться неизменным навсегда. Если другой пользователь позднее отредактировал студента, браузер может получить уведомление, перечитать API и показать новые сведения. Это обычное обновление уже работающего приложения. SSR отвечает за начальный документ, а дальнейшая свежесть требует самостоятельного механизма. Поэтому отсутствие нового HTML-документа при live-обновлении не означает, что первоначальный SSR перестал быть настоящим; просто разные этапы используют разные способы получения результата.

## Streaming SSR и постепенная готовность страницы

### Передать готовое, пока остальное ожидается

В простой схеме SSR сервер ожидает обязательные данные, формирует страницу и лишь затем отдает итоговое содержимое. Если один независимый блок медленный, он способен задержать весь экран. Streaming SSR позволяет передавать готовые части ответа по мере появления. Браузер получает каркас и доступное содержимое раньше, пока другие части еще находятся в работе.

Лекция 10, слайды 45–50, показывает карточку студента рядом с медленно получаемой историей оценок. Пока история не готова, на ее месте находится fallback — временное представление ожидания, например скелетон. Основной каркас страницы называют shell. Когда данные блока готовы, соответствующий механизм рендеринга доставляет результат и заменяет fallback.

Такое поведение не ускоряет медленный API-запрос. Оно убирает необходимость задерживать из-за него уже готовые независимые части. Если же все содержимое страницы зависит от одного обязательного результата, преимущество будет меньше. Например, нельзя безопасно показать персональные данные прежде, чем получена необходимая проверка доступа, просто ради раннего первого байта.

Нужно также различать передачу частей одного HTML-ответа и последующие обращения приложения. Если браузер сначала получил полностью завершенный пустой документ, а затем через API добавил список, это само по себе CSR-загрузка данных, а не доказательство Streaming SSR. SSE, которое используется в lab5 для уведомлений, тоже является другим механизмом: оно сообщает о дальнейших изменениях данных, а не постепенно формирует первоначальный HTML.

### Для чего нужна граница ожидания

Suspense обозначает механизм, который связывает асинхронную зависимость с тем местом интерфейса, где нужно отобразить ожидание. Несколько независимых границ позволяют не заменять весь экран одним индикатором. Например, профиль готов, рекомендации еще ожидаются, но навигация уже доступна. Выбор границ должен соответствовать структуре данных и пользовательским действиям, а не числу компонентов в папке.

Однако одинаковое название не гарантирует одинакового поведения библиотек. React Suspense участвует в потоковом серверном рендеринге и выборочной гидратации. Vue `<Suspense>` организует ожидание асинхронных зависимостей дерева компонентов; его API и интеграция отличаются. Наличие `await useAsyncData(...)` в странице Nuxt не позволяет без дополнительных доказательств объявить, что готовые HTML-блоки этой страницы уже передаются независимо.

В lab5 используется обычная серверная подготовка начальных данных. Здесь нет отдельно реализованной схемы потоковой выдачи независимых частей страницы. Тема Streaming SSR присутствует в вопросах ТЗ, поэтому знать ее нужно, но выдавать ее за выполненную функцию проекта нельзя. Различия механизмов описывают [React streaming SSR](https://react.dev/reference/react-dom/server/renderToPipeableStream) и [Vue Suspense](https://vuejs.org/guide/built-ins/suspense.html).

### Progressive и selective hydration

Progressive hydration означает, что интерактивность появляется по частям, а не обязательно сразу во всем дереве. Selective hydration добавляет выбор приоритета: взаимодействие пользователя может сделать определенный блок более срочным. Например, уже видимые фильтры важнее для человека, который пытается их открыть, чем находящаяся ниже второстепенная область.

В лекции 10, слайд 51, эти идеи показаны на нескольких блоках страницы и связаны с Suspense в обсуждаемой React-модели. При ответе важно называть контекст. Из рисунка нельзя заключить, что любой Vue-компонент автоматически получает тот же алгоритм. Nuxt имеет собственные возможности отложенной гидратации, например по появлению компонента в области видимости или взаимодействию; они описаны в [документации компонентов Nuxt](https://nuxt.com/docs/4.x/directory-structure/app/components#delayed-or-lazy-hydration).

Возможное уточнение на защите: **«Streaming и selective hydration — одно и то же?»** Нет. Streaming относится к тому, когда браузер получает части серверного результата. Выборочная гидратация относится к тому, какие части уже полученного интерфейса становятся интерактивными раньше. Эти механизмы могут работать вместе, но передача HTML и подключение поведения остаются разными этапами.

## Server и Client Components: общая задача и разные API

### Компонент, отрендеренный сервером, еще не React Server Component

Обычная Vue-страница lab5 участвует в SSR, а затем работает в браузере. Ее серверный HTML не превращает ее в React Server Component. RSC — отдельная модель React, обсуждаемая в лекции 10, слайды 52–56. В ней часть компонентов выполняется в серверном окружении, а их реализация не отправляется браузеру для обычного клиентского выполнения. Они передают результат дальше, сочетаясь с компонентами, которым нужна интерактивность.

Server Component может получать серверные данные и использовать возможности своего окружения. Client Component нужен для клиентского состояния, обработчиков и браузерных API. Например, серверная часть подготавливает сведения о студенте, а клиентская кнопка открывает редактор. Важен не внешний вид: даже очень сложная таблица может быть только отображением данных, тогда как маленькой кнопке требуется работающий обработчик.

Через такую границу передают поддерживаемые сериализуемые значения. Нельзя считать, что обычное замыкание обработчика со ссылками на серверную память можно отправить как JSON и продолжить выполнять в браузере. Серверные функции, предоставляемые некоторыми механизмами React, являются отдельной темой; они не делают произвольный `onClick` переносимым объектом памяти. Для основ вопроса достаточно уверенно различать данные и локальное поведение.

### Что означает `use client`

В React-приложении с RSC директива `'use client'` задает границу клиентского графа модулей. Ее не требуется ставить в каждом транзитивно импортированном компоненте: клиентская область включает соответствующие зависимости. При этом Server Component, переданный как готовый результат через `children`, не становится автоматически клиентским только из-за визуального вложения в интерактивную оболочку.

Особенно легко ошибиться в слове Client. В Next.js при первом открытии HTML может быть предварительно построен и для Client Components, после чего они гидратируются. Поэтому `'use client'` не равнозначно «этот компонент никогда не участвует в серверной подготовке HTML». Директива разделяет модель выполнения и клиентские зависимости, а не универсально отключает SSR. Сама модель описана в [документации React](https://react.dev/reference/rsc/use-client), а путь первого открытия — в [документации Next.js](https://nextjs.org/docs/app/getting-started/server-and-client-components).

### Как правильно связать вопрос с Nuxt

В своей реализации нужно показать соответствующие реальные средства: `import.meta.client` и `import.meta.server` для ветвей окружения, браузерные lifecycle-хуки для действий после монтирования, серверный каталог для Nitro-кода и SSR-совместимую загрузку данных страниц. Nuxt также предоставляет собственные client-only и server-only компоненты, но их нельзя отождествлять с React RSC по совпадению слов. В текущей lab5 отдельная архитектура островных компонентов не используется.

Суффикс `.client.vue` у компонента Nuxt и React-директива `'use client'` поэтому не являются взаимозаменяемой записью одного правила. Еще важнее не делать все страницы браузерными ради доступа к `window`: такой выбор убрал бы обязательное серверное содержимое. Нужно отделять конкретное браузерное действие от той части компонента, которая успешно формирует HTML на сервере.

Возможное уточнение на защите: **«Где выполняется ваш `profile.vue`?»** При прямом открытии его обычный код участвует в создании серверной страницы, затем клиентского приложения при гидратации; браузерные ветви ограничены отдельно. Начальный профиль приходит через сессию и `useAsyncData`. Это универсальная Vue-страница Nuxt, а не React Server Component. Для такого ответа важнее назвать два исполнения и их состояние, чем перечислить все модные виды компонентов.

## Файловая маршрутизация: от адреса к компоненту

### Что именно задает структура файлов

У страницы есть адрес, но сам адрес еще не содержит ее интерфейс. Получив `/students/42`, приложение должно выбрать компонент, извлечь параметр `42`, проверить доступ и получить данные. Маршрутизация решает первую часть этой цепочки: сопоставляет адрес правилу и странице. Она не доказывает существование студента и не выдает права на чтение записи.

В обычном Vue-приложении разработчик может вручную описать массив маршрутов Vue Router. Nuxt строит его по соглашениям каталога `app/pages`. Это и называют файловой маршрутизацией. Список компонентов остается реальным; просто его описание получается из файлов, а не поддерживается отдельно в большом массиве. В [страницах lab5](frontend/app/pages/index.vue) используются такие соответствия:

| Файл внутри `frontend/app/pages` | Адрес |
| --- | --- |
| `index.vue` | `/` |
| `login.vue` | `/login` |
| `register.vue` | `/register` |
| `profile.vue` | `/profile` |
| `students/new.vue` | `/students/new` |
| `students/[id]/index.vue` | `/students/42` для конкретного значения ID |
| `students/[id]/edit.vue` | `/students/42/edit` |

Квадратные скобки обозначают динамический сегмент. Компонент один, а значений сегмента много. Для каждого студента не требуется создавать новый `.vue`-файл. Внутри компонента параметр доступен через `useRoute().params.id`. В лекции 10, на слайдах 30–33, показаны аналогичные соглашения нескольких метафреймворков. Названия файлов у них различаются: `page.tsx` из примера Next.js нельзя механически перенести в Nuxt.

Статический адрес `/students/new` и динамический `/students/[id]` тоже различаются. Слово `new` выбирает предусмотренную статическую страницу; оно не должно интерпретироваться бизнес-логикой как ID нового студента. Не стоит заменять эти соглашения ручным разбором строки URL внутри каждого компонента: маршрутизатор уже выделяет путь и параметры.

Параметр пути и query-параметр имеют разное назначение. В `/students/42?tab=details` значение `42` выбирает запись, а `tab` может описывать режим ее отображения. Это не два разных ID. У маршрута также есть `meta`: сведения, объявленные самим приложением, например требование административной роли. Пользовательский query не заменяет `meta`: дописать `?admin=true` к адресу не означает получить метаданные администратора. При этом любые значения, поступившие из URL, остаются входными данными и не должны напрямую превращаться в доверенный SQL или право на операцию.

### Параметр маршрута еще не является корректным ID

В [карточке](frontend/app/pages/students/[id]/index.vue) код приводит параметр к строке, проверяет запись положительного целого числа и безопасный числовой диапазон. Значения `abc`, `-2` или слишком длинная последовательность цифр не становятся допустимыми ID только потому, что соответствуют динамическому маршруту. Для этого приложения такие адреса приводят к `404`.

Но и корректное число не подтверждает существование записи. `/students/42` может ссылаться на удаленного студента. Поэтому после проверки формы параметра нужен запрос API, а окончательное отсутствие устанавливает backend. Здесь две разные проверки: допустимо ли вообще искать такую запись и существует ли запись сейчас. Отдельная клиентская проверка не отменяет серверную валидацию входных данных.

Возможное уточнение на защите: **«Почему динамический маршрут нашел страницу, а ответ все равно 404?»** Маршрутизатор нашел компонент, способный обработать такой адрес. Затем приложение выяснило, что нужного ресурса нет. `404` может означать как отсутствие маршрута, так и отсутствие студента за существующим шаблоном маршрута.

### Вложенный путь, вложенный компонент и layout

Вложенные адреса отражают иерархию URL: `/students/42/edit` находится глубже `/students/42`. Но папка в файловом дереве сама по себе не требует одновременно показывать две страницы. Для вложенного отображения Nuxt использует родительский компонент с собственным `<NuxtPage>`, в который подставляется дочерний маршрут. В текущей lab5 у карточки и редактора отдельные компоненты; над ними нет дополнительной родительской страницы `students/[id].vue` с таким местом для дочернего содержимого.

Layout решает другую задачу: сохраняет общую структуру нескольких страниц. Шапка, меню и боковая панель не должны копироваться во все компоненты. При клиентской навигации общий layout может оставаться смонтированным, поэтому его состояние сохраняется. При полной загрузке документа создается новое приложение: ожидать сохранения обычного локального состояния старого компонента уже нельзя. Этот смысл layout показан на слайде 34 лекции 10.

В Nuxt для выбираемых layouts предусмотрены `app/layouts`, `<NuxtLayout>` и метаданные страницы. Однако в нашей реализации отдельные layout-файлы не используются. Общая шапка и `<NuxtPage>` находятся в [app.vue](frontend/app/app.vue), потому что оболочка одна. На защите точнее сказать: «Общий интерфейс вынесен в корневой компонент; механизм выбираемых Nuxt layouts здесь не потребовался». Это проще, чем называть существующим файл `layouts/default.vue`, которого нет. Разницу между этими способами описывает [документация layouts](https://nuxt.com/docs/4.x/directory-structure/app/layouts).

Свойство `:page-key="pageRoute => pageRoute.path"` у `<NuxtPage>` связывает экземпляр страницы с путем. При изменении пути компонент получает новый жизненный цикл; это полезно для карточек разных студентов. Query-параметры в `path` не входят. Поэтому этот ключ не означает «любое изменение URL обязательно пересоздаст весь интерфейс».

## Клиентская навигация и предварительная загрузка

### Почему один адрес открывается двумя путями

Уже разобранное различие SSR и SPA проявляется в выборе ссылки. Прямое открытие запрашивает документ; внутренний переход обычно использует существующее приложение и загружает только недостающие ресурсы. На слайде 35 лекции 10 показаны эти две точки начала работы. Теперь важно понять, чем конкретно Nuxt-ссылка отличается от нативной.

Обычный `<a href="/profile">` тоже является ссылкой, но по умолчанию приводит к полной навигации браузера. `<NuxtLink>` для внутреннего маршрута связывает ссылку с Vue Router. В [error.vue](frontend/app/error.vue) обычный `<a href="/">` выбран специально: после глобальной ошибки нужен новый документ с заново определенной сессией. Это локальное решение для восстановления, а не основание заменить все ссылки приложения обычными переходами.

### Что prefetch ускоряет и какой у него расход

Prefetch — предварительное получение ресурсов до перехода. Например, пользователь еще читает список, а приложение уже может получить код страницы, ссылка на которую появилась в видимой области. Если человек затем нажмет ссылку, часть сетевого ожидания уже завершена. Это изменение момента работы, а не увеличение скорости самого сервера.

В Nuxt у `<NuxtLink>` есть механизм предварительной загрузки; условия можно настраивать, например по видимости или взаимодействию. Однако из этого нельзя заключать, что браузер обязательно заранее выполнил каждый API-запрос любой SSR-страницы. Набор предварительно получаемых ресурсов зависит от режима и возможностей приложения. В lab5 нет собственной системы, которая при показе всех ссылок заранее загружает карточки всех студентов. Возможности компонента описаны в [официальной документации](https://nuxt.com/docs/4.x/api/components/nuxt-link).

На слайде 36 лекции 10 рядом с prefetch написано про уменьшение трафика. Это полезно понимать с оговоркой: **prefetch сам по себе не гарантирует меньше переданных байтов**. Человек может не открыть подготовленную страницу, и тогда ресурсы были получены зря. Возможный выигрыш — меньшая задержка после клика; возможная цена — дополнительные запросы, трафик и работа сервера. Для множества тяжелых ссылок агрессивная предварительная загрузка способна ухудшить результат.

Возможное уточнение на защите: **«Если код страницы уже получен через prefetch, можно пропустить проверку доступа?»** Нет. Наличие кода не подтверждает права текущего пользователя. За время между подготовкой и переходом сессия могла измениться, а Java отдельно проверяет каждый защищенный API-запрос.

## Middleware: навигация, перенаправления и окончательные права

### Одинаковое слово обозначает разные проверки

Middleware — промежуточная обработка до следующего этапа. Но полезно сразу спросить: до какого именно этапа и в какой среде? В Nuxt route middleware участвует в переходе на страницу. Серверное middleware Nitro обрабатывает HTTP-запрос. Фильтры Spring Security проверяют обращение к Java. У этих механизмов разные аргументы, время выполнения и границы ответственности.

В [auth.global.js](frontend/app/middleware/auth.global.js) аргумент `to` описывает маршрут назначения. Файл получает метаданные страницы и состояние пользователя, затем разрешает переход или возвращает перенаправление. Суффикс `.global` включает его для маршрутов приложения. Сам код сразу пропускает страницы, у которых нет ни `auth`, ни `guest`; значит, глобальность регистрации не равна обязательной одинаковой проверке каждого экрана.

Флаги `auth`, `guest` и `admin` являются соглашениями проекта. Nuxt не предоставляет авторизацию автоматически после записи `auth: true`. Механизм работает потому, что middleware читает этот флаг. Страница профиля помечена `auth: true`, вход и регистрация — `guest: true`, создание и редактирование студентов дополнительно требуют `admin: true`.

Порядок важен: сначала `await $session.loadUser()`, затем решения по `auth.user` и роли. Если сразу считать начальное `user: null` гостем, можно перенаправить еще не проверенного вошедшего человека на вход. Известное отсутствие пользователя и незавершенная проверка являются разными состояниями. При SSR нужные сведения должны быть выяснены до нормального рендеринга защищенной страницы.

### Почему перенаправление надо вернуть

Основные решения текущего middleware выглядят так:

```js
if (protectedPage && !auth.user) return navigateTo('/login', { replace: true })
if (to.meta.admin && !auth.isAdmin) return navigateTo('/', { replace: true })
if (guestPage && auth.user) return navigateTo('/', { replace: true })
```

Гость идет на вход, USER с административного экрана возвращается к списку, вошедший посетитель гостевой страницы тоже получает список. `return` передает результат маршрутизатору и прекращает обычное продолжение этого middleware. Без корректного возврата можно выполнить лишние действия после решения о переходе. Такое соглашение описано в [документации route middleware](https://nuxt.com/docs/4.x/directory-structure/app/middleware).

На сервере перенаправление оформляется HTTP-ответом с `Location`; для обычного `navigateTo` стандартный код — `302`. Браузер затем запрашивает новый адрес. В уже работающем клиентском приложении переход выполняет маршрутизатор: это не отдельный серверный ответ `302` на каждый клик. Параметр `replace: true` влияет на историю переходов; его не следует путать с кодом HTTP.

Еще одна опасность — цикл перенаправлений. Если требовать вход на самой странице входа, гость может бесконечно возвращаться туда же. Если отправлять любого пользователя с любого адреса на одну и ту же защищенную страницу, проблема повторится. Поэтому правила должны учитывать назначение страницы и конечные состояния, а не просто вызывать redirect в любом сомнительном случае.

Route middleware работает и при первоначальной серверной подготовке, и в браузере при начальной загрузке и последующих переходах. Повторное выполнение не означает, что обязательно повторяется каждый HTTP-запрос. Менеджер может воспользоваться уже известным состоянием, которое пришло через SSR. Флаг `checked` означает именно принятое приложением знание, а не обещание, что сессия на сервере не изменится никогда. Поэтому точнее объяснять конкретное условие повторной проверки, чем говорить «middleware один раз проверил пользователя навсегда».

У Nitro другой масштаб: его обработчик видит HTTP-event и может подготовить заголовки ответа, но не является Vue-наблюдателем за страницей. В lab5 серверный auth-плагин использует request-hook, чтобы дать HTTP-запросу собственный контекст. А файл в `server/routes` непосредственно отвечает на подходящий адрес API. Слово `server` указывает место выполнения, но само по себе не превращает такой обработчик в бизнес-авторизацию Java.

### Почему Java остается обязательной

Возможное уточнение на защите: **«Зачем Spring Security, если middleware уже не пускает USER в редактор?»** Пользователь может обратиться к API напрямую, вообще не открывая страницу редактора. Route middleware такого запроса не увидит. Оно управляет навигацией, а Spring Security принимает окончательное решение о серверной операции. Аналогично скрытая кнопка удаления улучшает интерфейс, но не защищает endpoint.

В [SecurityConfig](backend/src/main/java/ru/itmo/students/security/SecurityConfig.java) GET `/api/requests/**` и QUERY `/api/requests` разрешены USER и ADMIN; изменение студентов требует ADMIN. Для `/api/auth/me` требуется аутентификация. Не следует говорить, будто любой адрес API без исключения доступен только администратору: публичные auth-операции и чтение профиля имеют другие правила.

Если обязательная проверка пользователя завершилась технической ошибкой, middleware не объявляет посетителя гостем. Оно создает ошибку Nuxt со статусом обращения либо `503`. Иначе остановленный backend выглядел бы как неверный пароль, а полезная информация о причине отказа исчезла бы. Только окончательный отказ аутентификации позволяет менеджеру сессии определить гостевое состояние.

## Серверная загрузка данных и состояние конкретного запроса

### Зачем между браузером и Java находится Nuxt

Java по-прежнему владеет данными, правилами и авторизацией. Nuxt обращается к ней как клиент API, чтобы подготовить HTML. При прямом открытии карточки цепочка имеет вид: браузер запрашивает документ, Nuxt выясняет пользователя, запрашивает студента, получает JSON и строит разметку. Это frontend-задача, хотя часть работы выполняется на сервере. Перенос получения данных в SSR не означает перенос jOOQ, паролей или SQL в Nuxt.

В браузере lab5 использует относительные `/api/...`; [Nginx](nginx/default.conf) направляет большую часть API в Java. Только `login`, `logout` и `refresh` выделены в обработку Nitro. Серверная ветка клиента обращается к Java по внутреннему `runtimeConfig.backendUrl`. Браузеру этот внутренний адрес не нужен. Серверный и клиентский код могут запрашивать одну логическую операцию, но иметь разные способы доставки HTTP-запроса.

Здесь особенно легко перепутать fetch с полной процедурой загрузки страницы. Сетевой запрос получает ответ. Затем еще надо прочитать тело, обработать неуспешный статус, связать данные с состоянием и передать серверный результат клиенту. Один вызов сети не выполняет автоматически все эти обязанности.

### `fetch`, `$fetch`, `useFetch` и `useAsyncData`

Нативный `fetch` возвращает Promise объекта `Response`: с кодом, заголовками и телом. Обычно он не отклоняет Promise только из-за HTTP `404`; приложение должно проверить статус. Поэтому собственный `api.js` отдельно разбирает ответы и создает ошибки. У `fetch` есть полезные низкоуровневые возможности, но нет встроенного соглашения «положить этот результат в Nuxt payload».

Nuxt `$fetch` — другой инструмент: функция на основе ofetch, удобная для получения уже разобранных данных. Ее не следует отождествлять с нативным fetch по формату результата и обработке HTTP-ошибок. Но одиночный `$fetch` в setup тоже не решает сам по себе передачу результата между SSR и гидратацией.

`useAsyncData` связывает асинхронный обработчик, ключ и данные Nuxt. В lab5 он оборачивает собственный сервис студентов или менеджер сессии, поэтому не требует заменить общий клиент на `$fetch`. `useFetch` является удобным сочетанием `useAsyncData` и `$fetch` для запроса по адресу. Это альтернатива для подходящих случаев, а не доказательство неправильности собственного клиента. Их назначение описано в документации [useAsyncData](https://nuxt.com/docs/4.x/api/composables/use-async-data) и [useFetch](https://nuxt.com/docs/4.x/api/composables/use-fetch).

Возможное уточнение на защите: **«Почему нельзя просто поставить fetch в onMounted?»** Тогда запрос появится только после монтирования в браузере. Сервер не получит нужные данные для первоначального HTML, и заявленный SSR этих данных исчезнет. Начальное чтение должно участвовать в серверной подготовке, а mounted-поведение подходит для последующих браузерных действий и подписок.

### Payload позволяет продолжить готовую загрузку

У карточки используется ключ с ID пользователя и студента:

```js
'students:card:' + auth.user.id + ':' + id
```

Ключ связывает конкретный результат с данными Nuxt. Обработчик получает студента, сервер строит HTML и передает сериализуемый результат браузеру в payload. При обычной гидратации этот результат позволяет не повторять начальное получение только ради восстановления того же состояния. Payload — переданные данные, а не продолжающий жить в браузере серверный объект и не секретное хранилище.

В обработчике нужно вернуть результат. Если он только побочно запишет переменную и вернет `undefined`, Nuxt не получит нормальных данных этой загрузки; возможно повторное выполнение на клиенте. В профиле обработчик возвращает пользователя, а отсутствие результата превращает в явно обработанную ошибку. Отдельно важно не помещать в payload пароли, токены или чужие сведения: браузер способен прочитать переданное ему содержимое.

`useAsyncData` предоставляет реактивные `data`, `error` и `status`, а также функции повторного выполнения и очистки. В `<script setup>` у ref читают `.value`; в шаблоне Vue распаковывает его. Наличие `await useAsyncData(...)` позволяет следующему коду setup анализировать завершившийся результат. При обычной блокирующей загрузке новая страница ожидает данные; `lazy` является отдельным способом изменить ожидание навигации, а не синонимом SSR.

В реальной карточке есть также `onMounted(() => load())`. Поэтому нельзя обещать «после SSR вообще нет клиентских чтений». Payload предотвращает ненужное повторение самого начального `useAsyncData`, а явно написанная mounted-загрузка является другой операцией: она проверяет актуальность карточки после серверной стадии. Объяснение должно учитывать обе строки, а не выводить поведение всего проекта из одного общего правила Nuxt.

### Где живут Pinia, сервисы и конфигурация

На сервере одновременно обрабатываются страницы разных пользователей. Значит, обычная общая переменная модуля `currentUser` была бы опасным местом для персональных сведений. В lab5 Nuxt создает приложение для SSR-запроса, а плагины создают API и session внутри его функции. Store получается через Pinia этого приложения. Нельзя подменять это одним общим экземпляром пользователя на весь Node-процесс.

В браузере срок жизни другой: приложение и его сервисы обычно переживают несколько переходов. Поэтому шапка и профиль видят одно состояние Pinia, а каждый новый маршрут не создает независимую авторизацию. `provide` плагина делает сервис доступным как `$session` или `$api`; компонент получает готовую зависимость через `useNuxtApp`, а не создает свою копию клиента в каждом обработчике.

Такую передачу готовых зависимостей называют dependency injection, внедрением зависимостей. В данном случае за термином стоит простая операция: окружение создает нужный объект и предоставляет его компонентам. Это не требование построить универсальный контейнер вручную. Нумерация плагинов `01.session` и `02.students` отражает реальную зависимость: студенческий сервис получает API, созданный раньше.

Runtime-конфигурация тоже имеет границы. `backendUrl` расположен вне `public`, поэтому предназначен серверу Nuxt. Общедоступные настройки попадали бы в клиентское окружение. Но даже серверный параметр нельзя считать безопасно скрытым, если затем самостоятельно включить его в возвращаемый объект страницы: окончательную границу определяет то, какие данные действительно отправлены браузеру.

### Контекст Nuxt не является глобальным текущим пользователем

Функции вроде `useNuxtApp`, `useState` и `useRequestEvent` должны понимать, с каким приложением работают. Это называют контекстом Nuxt. Отсутствие явного аргумента в каждом вызове не означает существование одной общей страницы на весь сервер. Окружение связывает вызов с нужным SSR-приложением или браузерным экземпляром.

У обычного callback, вызванного позднее после сетевого ответа, такой контекст может отсутствовать. Поэтому в плагине встречается `nuxtApp.runWithContext(...)`: выполнение явно связывается с сохраненным экземпляром приложения. Например, так вызывается навигация после истечения сессии. Это способ получить правильное окружение для Nuxt API, а не блокировка запросов и не создание новой сессии. Еще проще, когда возможно, заранее получить нужный сервис и затем пользоваться его обычными методами.

Автоматические импорты тоже не означают универсальные глобальные функции JavaScript. Nuxt обрабатывает свои компоненты и знает, откуда брать `useAsyncData` или `definePageMeta`. Если перенести такую строку в произвольный Node-скрипт, само имя там не появится. На защите важно различать возможность языка, библиотечный API и соглашение метафреймворка: это объясняет, почему похожие по виду файлы имеют разные условия выполнения.

## Последовательные запросы, параллельность и request waterfall

### `await` приостанавливает продолжение функции

Request waterfall — цепочка ожиданий, в которой следующая работа начинается только после предыдущей. Иногда это необходимо: прежде чем запрашивать разрешенные пользователю данные, нужно определить самого пользователя. Но если три независимых раздела ждут друг друга просто из-за расположения `await`, страница теряет время без полезной причины. В лекции 10, на слайдах 60–62, эта разница показана для профиля, оценок и комментариев.

Условные независимые операции можно записать последовательно:

```js
const student = await getStudent(id)
const grades = await getGrades(id)
const comments = await getComments(id)
```

Это учебный пример, а не три существующих endpoint нашей lab5. Если каждая операция длится около 300 мс и прочие расходы малы, суммарное ожидание будет около 900 мс. Следующий вызов начинается после завершения предыдущего `await`. Сам `await` не блокирует весь серверный процесс: он приостанавливает продолжение этой асинхронной функции, пока другая работа может выполняться.

Для независимых данных можно получить Promise нескольких операций до ожидания:

```js
const [student, grades, comments] = await Promise.all([
  getStudent(id),
  getGrades(id),
  getComments(id)
])
```

Массив аргументов вычисляется перед вызовом `Promise.all`, поэтому функции уже вызываются и возвращают Promise. `Promise.all` объединяет их ожидание, а не создает три JavaScript-потока и не начинает сетевую работу магически. В идеальном случае ожидание будет близко к самому медленному запросу: здесь около 300 мс. Реальная сеть, ограничения соединений и конкуренция за backend способны изменить числа.

### Ошибки и зависимости ограничивают параллельность

Возможное уточнение на защите: **«Если один Promise упал, остальные отменяются?»** Нет. Общий Promise отклоняется по первому отказу, но уже выполняющиеся операции сами собой не прекращаются. Для отмены нужен отдельный механизм, например AbortSignal, поддержанный операцией. Еще одно свойство: массив успешных результатов сохраняет порядок входных Promise, а не порядок их завершения.

`Promise.allSettled` ожидает завершения всех операций и возвращает для каждой результат или причину отказа. Это подходит, когда части интерфейса могут жить независимо и нужен полный набор исходов. `Promise.all` удобен, когда для продолжения нужен успешный общий результат. Выбор определяется смыслом экрана, а не правилом «всегда бери более продвинутый метод».

Полезно сравнить три формы ожидания. `await first(); await second()` задает последовательность вызовов. Если сначала сохранить `const one = first()` и `const two = second()`, а затем отдельно ждать `one` и `two`, вызовы уже произошли до первого ожидания. Следовательно, последовательные строки `await` сами по себе не доказывают последовательное выполнение сетевых операций: важен момент создания Promise. Наконец, `await Promise.all([first, second])` с самими функциями вообще не вызывает их. В массив должны попасть нужные значения или результаты вызова, а не надежда, что `Promise.all` исполнит произвольный список функций.

Эта тема особенно удобна для уточняющего вопроса, потому что одной фразы «асинхронность делает быстрее» недостаточно. Асинхронность позволяет не занимать поток ожиданием внешнего события; сокращение времени конкретной страницы появляется только тогда, когда удается перекрыть независимые ожидания. Если backend последовательно держит общий ресурс или второй запрос требует результата первого, наличие Promise не устраняет эту зависимость.

В нашей защищенной SSR-странице порядок «получить пользователя, затем данные» является осмысленной зависимостью. Студенческий сервис использует идентичность пользователя, а маршрут должен решить, допустим ли экран. Механическое распараллеливание этих этапов может преждевременно отправить запрос или использовать неправильное состояние. Сначала надо разделить необходимые зависимости и случайные ожидания; только вторые можно убирать без изменения поведения.

## Loading, Error и Not Found: состояния и HTTP-ответы

### Ожидание не является ошибкой или пустым результатом

Пока данные еще не получены, приложение находится в состоянии загрузки. Это отличается от успешного пустого списка и от отказа запроса. Если все три случая представить одним `[]`, человек не поймет, идет ли поиск, студентов нет или backend недоступен. Поэтому нужны отдельные сведения о ходе и результате обращения.

В lab5 [app.vue](frontend/app/app.vue) содержит `NuxtLoadingIndicator` для переходов, профиль использует `status` загрузки Nuxt, а список и карточка имеют собственные индикаторы последующих чтений. При первоначальном блокирующем SSR текст «Загрузка...» не обязан сначала появиться в документе пользователя: сервер может дождаться данных и вернуть готовый HTML. Индикатор особенно нужен при клиентских переходах, повторных запросах и изменениях уже открытого экрана.

Занятость формы тоже не равна загрузке всей страницы. Пока сохраняется запись, можно заблокировать повторную отправку и показать сообщение у формы. При временном отказе не обязательно уничтожать весь интерфейс. Выбор масштаба ошибки зависит от операции: можно ли продолжить работу с уже показанными данными или отсутствует обязательное основание для самой страницы.

### Коды описывают разные причины

| Код | Смысл для этой лабораторной |
| --- | --- |
| `200` | Успешное получение данных или документа |
| `201` | Создание аккаунта или другого ресурса согласно контракту endpoint |
| `204` | Успех без тела, например auth-операция |
| `302` | Серверное перенаправление на другой адрес |
| `400` | Некорректный запрос или данные |
| `401` | Аутентификация не принята |
| `403` | Запрос запрещен; причиной могут быть права или CSRF |
| `404` | Маршрут или ресурс не найден |
| `409` | Конфликт, например занятое уникальное значение |
| `503` | Сервис временно недоступен либо клиент преобразовал сетевой сбой в такую ошибку |

Текст на экране сам по себе не задает HTTP-код. Если сервер вернул документ `200` с надписью «не найдено», для HTTP это успешный документ. Поэтому при SSR ошибки надо согласовать с реальным статусом ответа. В профиле для ошибки используется `setResponseStatus`, а первоначальная ошибка карточки преобразуется в `createError` с нужным `statusCode`.

Возможное уточнение на защите: **«Чем 401 отличается от 403?»** В первом случае не принята аутентификация. Во втором сервер запрещает обращение; это может быть недостаточная роль или CSRF. Обновление access не сделает USER администратором, а технический `503` вообще не является доказательством отсутствия пользователя. Если смешать статусы, приложение начнет ошибочно выходить из аккаунта или бесполезно повторять запрещенные действия.

### Локальное сообщение и глобальная ошибка

В `useAsyncData` ошибка доступна через реактивный `error`; это еще не требование заменить весь экран. Профиль показывает сообщение и кнопку повторения, а карточка при невозможности первоначально получить обязательную запись создает ошибку страницы. При live-удалении открытого студента код явно вызывает `showError` и очищает старый объект: прежняя карточка не должна выглядеть существующей.

Глобальную разметку задает [error.vue](frontend/app/error.vue). Она получает ошибку и различает `404` с остальными случаями. Не нужно искать в Nuxt обязательные `not-found.tsx` или `error.tsx` из примеров Next.js: соглашения метафреймворков различаются. На сервере брошенный `createError` способен сформировать страницу ошибки и статус; для глобальной клиентской ошибки существует `showError`. Нельзя считать любое пойманное исключение автоматической сменой всего документа. Общее поведение описывает [руководство Nuxt по ошибкам](https://nuxt.com/docs/4.x/getting-started/error-handling).

Возвращение из глобальной ошибки через обычную ссылку создает новый HTTP-запрос. Сессия и данные определяются заново. Такой переход может привести к списку, странице входа или новому сообщению недоступности — в зависимости от текущего состояния сервера и пользователя. Сама кнопка «На главную» не обещает, что причина ошибки уже устранена.

## Кеш: что хранится, когда устаревает и кому принадлежит

### Сначала назвать сохраненный объект

Пусть пользователь второй раз открывает карточку студента. Можно повторно получить запись у Java, а можно использовать уже полученный результат. Кеширование означает сохранение результата ради такого повторного использования. Выигрыш понятен: меньше обращений к источнику и меньше ожидания. Цена тоже конкретна: сохраненный результат способен устареть, занять память или попасть не тому пользователю. Поэтому ответ «у нас есть кеш» без уточнений почти ничего не объясняет.

На слайде 63 лекции 10 разделены ресурсы, данные и результат рендера. Ресурсами могут быть JavaScript, CSS и изображения. Данными — JSON списка студентов. Результатом рендера — готовый HTML страницы. Это разные объекты с разными правилами обновления. Изменение имени студента не требует заново скачивать прежнюю картинку, но требует перестать показывать старое имя. И наоборот, обновление стилей не означает, что профиль пользователя изменился.

Место хранения тоже бывает разным. Браузерный HTTP-кеш повторно использует ответы по правилам HTTP. Общий прокси или CDN может обслуживать несколько браузеров. Кеш приложения представляет собой структуры данных в его памяти. PostgreSQL и операционная система имеют собственные механизмы ускорения чтения, но они не заменяют правила свежести интерфейса. Нельзя ответить на вопрос о пользовательском кеше рассказом только о том, что база хранит страницы в оперативной памяти.

В Nuxt есть еще передача результатов первоначальной загрузки в payload. Она позволяет браузерному приложению получить данные, использованные при SSR, и согласованно продолжить работу. Сам факт наличия payload не означает общий кеш HTML для всех посетителей. В lab5 дополнительно существует явно написанный кеш студентов через `useState('students-cache', ...)`. Его содержимое и срок действия определяет [students.js](frontend/app/utils/students.js), а не произвольная общая политика CDN.

Для любого такого механизма нужно назвать четыре вещи: что сохраняется, какой у результата ключ, до какого момента его можно использовать и что делает результат неактуальным. Пятый вопрос появляется в приложении с входом: какие пользователи имеют право получить сохраненные данные. Быстро отдать чужой ответ хуже, чем медленно получить правильный.

Возможное уточнение на защите: почему в проекте есть `no-store`, если по заданию нужен кеш? HTTP-заголовок ограничивает хранение HTTP-ответов, а собственный модуль отдельно хранит уже полученные объекты в состоянии текущего приложения. Это два разных уровня. Запрет общего хранения персонального HTML не запрещает разумно повторно использовать данные внутри своего пользовательского экземпляра.

### Cache hit, cache miss и ключ результата

Cache hit — ситуация, когда по ключу найден пригодный результат и политика разрешает его вернуть. Cache miss — отсутствие такого результата: источник придется прочитать. Запись может физически присутствовать, но быть просроченной; для политики, требующей свежие данные, это тоже не подходящий hit. Важно различать «значение нашлось в объекте» и «значение разрешено использовать».

Ключ описывает вопрос, на который отвечает результат. Один ключ `students` не подходит одновременно для страницы 1, страницы 2 и фильтра по общежитию. Если результат зависит от номера страницы, размера, сортировки и фильтров, эти параметры должны участвовать в ключе. Иначе кеш станет быстро выдавать ответ на другой запрос. Эта ошибка особенно неприятна: HTTP может работать правильно, но пользователь увидит не ту выборку без очевидного сообщения об ошибке.

В lab5 параметры списка сначала сортируются по именам, затем сериализуются. Два объекта с одинаковыми парами, записанными в разном порядке, поэтому дают одинаковый ключ. Это нормализация представления запроса, а не сортировка самих студентов. Ключ карточки содержит ID студента. К обоим вариантам добавляется ID пользователя, полученный через функцию `userId()`.

Пользовательская часть ключа полезна даже тогда, когда USER и ADMIN читают похожие сведения. Она явно закрепляет принадлежность результата, помогает при смене аккаунта и не позволяет будущему различию прав незаметно сломать разделение данных. Но наличие ID в строке не заменяет изоляцию серверного состояния. Если общий серверный объект ошибочно хранит текущего пользователя, сам способ вычисления ключа уже может оказаться неправильным.

TTL, time to live, задает срок пригодности записи. В проектном кеше это 30 секунд с момента сохранения результата. После этого следующий вызов чтения обращается к API. Отдельного таймера, который через 30 секунд самостоятельно отправляет запрос, здесь нет. Если страница вообще больше не обращается к модулю и не получает уведомлений, один TTL не заставит экран обновиться.

При оценке пользы кеша важен характер нагрузки. Если человек пять раз открывает одну карточку за короткое время, повторное использование помогает. Если каждый запрос содержит совершенно новый набор фильтров, подходящих hit почти не будет, а память все равно потребуется. Поэтому запись не обязательно нужно хранить бесконечно. В lab5 число ключей ограничено: перед добавлением при достижении 50 удаляется первый перечисленный ключ. Это простое ограничение объема, а не полноценная политика LRU, которая отслеживает недавнее использование.

Еще один отдельный механизм — объединение одновременно выполняющихся чтений. Сохраненный результат помогает только после получения данных. Если два вызова одновременно встретили miss, оба могут обратиться к источнику, пока первый еще не успел наполнить кеш. В студенческом `read` общего Promise для одинаковых ключей нет; приписывать ему такую дедупликацию нельзя. У HTTP-клиента объединение refresh действительно есть, но это другой объект и другая цель. Кеширование готового значения и совместное ожидание одной незавершенной операции нужно уметь различать.

Возможное уточнение на защите: гарантирует ли TTL в 30 секунд обновление экрана ровно через 30 секунд? Нет. Здесь TTL проверяется при чтении. Он ограничивает повторное использование записи, а автоматическое перечитывание открытого экрана обеспечивается другой цепочкой — уведомлением и реакцией страницы.

### HTTP-свежесть и проверка версии

Для HTTP-кеша важно различать хранение и использование без обращения к серверу. `Cache-Control: max-age=60` разрешает считать ответ свежим в течение указанного срока. `no-cache` допускает хранение, но требует проверки перед повторным использованием. `no-store` запрещает сохранять ответ в HTTP-кеше. `private` запрещает хранение общим кешем, но само по себе не запрещает личный кеш браузера. Поэтому `private` не означает шифрование или защиту от JavaScript. Семантика этих директив определена в [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html).

ETag — идентификатор версии представления. Сохраненное значение можно отправить через `If-None-Match`. Если представление не изменилось, сервер отвечает `304 Not Modified` без нового тела, и кеш использует сохраненное. Сеть при этом не исчезает: проверка тоже требует обмена. Такой путь экономит передачу тела, тогда как свежий hit способен обойтись без запроса к источнику. На слайде 65 лекции 10 показан именно этот смысл проверки версии.

`Vary` сообщает, какие поля запроса дополнительно участвуют в выборе варианта ответа. Например, ответы разных языков нельзя бесконтрольно смешивать. Но `Vary: Cookie` не следует объявлять универсальным решением для персональных страниц: большое количество разных cookies усложняет варианты, а ошибка политики все равно остается опасной. В lab5 выбран более прямой подход: персональные ответы Nuxt получают `private, no-store`, а допустимое повторное использование данных выполняется внутри своего экземпляра приложения.

Условные запросы и выбор варианта описаны в [HTTP Semantics, RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html). Полезно не путать их с самим алгоритмом приложения. ETag не вычисляется автоматически оттого, что где-то завели `useState`, а приложение не получает `304` только из-за наличия своего тридцатисекундного кеша. В этой лабораторной собственное чтение возвращает объект данных либо обращается к Java, без отдельного протокола ETag в студенческом модуле.

Возможное уточнение на защите: `304` — это пустые данные? Нет. Это ответ на условный запрос: прежнее тело можно продолжить использовать. Если у клиента вообще нет соответствующего сохраненного представления, такая схема не дает ему готовую страницу из ничего.

### Revalidation, инвалидация и SWR

Инвалидация означает, что прежнюю запись больше нельзя считать пригодной. Ее можно удалить или пометить устаревшей. Revalidation означает проверку актуальности либо получение обновленного результата по предусмотренной политике. Эти действия связаны, но не тождественны: удалить запись можно немедленно, а новое чтение выполнить только тогда, когда оно кому-то потребуется.

Лекция 10 на слайдах 66–67 отдельно ставит вопросы «когда обновлять?» и «что отдавать во время обновления?». Время и событие отвечают на первый. TTL признает запись старой после интервала. Событие признает ее старой после конкретного изменения, например сохранения студента. Можно сочетать оба условия: событие дает быструю реакцию, TTL ограничивает использование пропущенного старого результата при следующих чтениях.

Блокирующая стратегия сначала получает свежие сведения, затем возвращает их ожидающему вызову. SWR, stale-while-revalidate, допускает немедленно отдать старый результат и обновить его в фоне. При SWR интерфейс быстрее получает содержимое, но осознанно некоторое время показывает прошлое состояние. Это не ошибка сама по себе: вопрос в допустимости такого компромисса для конкретных данных.

Кеш lab5 не возвращает просроченную запись по SWR. Его `read` при истекшем сроке ожидает `load()`. Если на экране в это время еще видна предыдущая таблица, это состояние компонента во время загрузки, а не доказательство реализации SWR внутри кеша. Нельзя назвать любую старую картинку на экране «SWR» без понимания того, кто вернул старое значение и кто организовал фоновое обновление.

По расположению чтения и записи часто выделяют cache-aside: приложение проверяет кеш, при промахе читает источник и сохраняет результат. Студенческий модуль использует именно такую последовательность. При изменении он не пытается самостоятельно вычислить все новые варианты списков, а удаляет прежние результаты. Иногда применяют write-through, когда запись согласованно проходит через кеш к источнику, или write-behind, когда источник обновляется отложенно. Для нашей работы отложенная запись усложнила бы подтверждение сохранения и разбор ошибок, поэтому такой механизм здесь не нужен. Названия полезны для сравнения стратегий, но не следует перечислять их как уже реализованные функции.

Возможное уточнение на защите: достаточно ли увеличить TTL, чтобы сайт всегда был быстрее? Более долгий срок может поднять долю hit, но увеличивает риск старых данных. А при почти уникальных запросах пользы может не быть. Настройка TTL — выбор допустимой свежести для конкретной нагрузки, а не независимая кнопка ускорения.

### Изменение данных и запоздавший ответ

После успешного сохранения или удаления `students.js` вызывает `clear()`. Событие другого пользователя тоже очищает кеш. Очищаются все студенческие записи, поскольку одна правка может менять несколько выборок: позицию при сортировке, число страниц, попадание в фильтр и открытую карточку. Более точечная инвалидация возможна, но требует надежно вычислять все затронутые ключи. Для этой лабораторной простая общая очистка понятнее.

Здесь есть тонкая гонка. Чтение списка началось до изменения, затем кеш очистили, а старый HTTP-ответ пришел после очистки. Простого присваивания пустого объекта недостаточно: старый запрос может снова положить прошлые данные в новый кеш. Поэтому `clear()` увеличивает `version`, а `read` запоминает версию до `await` и сравнивает после него. Только совпадение разрешает запись результата.

Эта проверка защищает именно наполнение кеша. Она не отменяет отправленный HTTP-запрос и не обещает, что старый вызов не вернет данные своему потребителю. У компонентов и RxJS есть свои проверки актуальности и отмена. В разных местах похожие счетчики и сигналы нужны потому, что защищаются разные действия: запись в кеш, запись на экран и продолжение сетевой операции.

Состояние `useState` должно подходить для передачи с серверной стадии в браузер. В проектном кеше это обычные данные и числовое время истечения. Ни соединение с базой, ни функция получения данных, ни AbortController туда не складываются. Возможность SSR сама по себе не делает любой объект безопасно сериализуемым. Это ограничение отмечено в [документации Nuxt useState](https://nuxt.com/docs/4.x/api/composables/use-state). Клиент получает содержимое переданного состояния, поэтому в таком кеше также не место серверным секретам.

Возможное уточнение на защите: почему недостаточно просто очистить объект? Очистка изменяет состояние сейчас, а уже начатая функция продолжает выполнение позже. Версия связывает ее будущую запись с тем состоянием, при котором она начиналась. Без этого старое завершение способно отменить смысл очистки.

Цельную последовательность удобно представить на одной записи. Анна открыла студента 17, и модуль сохранил полученный объект. Через пять секунд Борис изменил его общежитие. У Анны срок записи еще не истек, поэтому без уведомления следующий вызов мог бы вернуть старое значение. Событие очищает кеш раньше TTL и просит открытую карточку перечитать запись. Новое чтение получает текущее общежитие, хотя прежние 30 секунд еще не закончились. Именно здесь видно, зачем сочетаются срок и событие: они срабатывают по разным основаниям.

Если Анна к этому времени закрыла карточку, не обязательно немедленно загружать все когда-либо открытые записи. Достаточно очистить устаревшие результаты; при следующем открытии нужный объект будет прочитан заново. Разделение «сделать запись непригодной» и «обязательно сейчас получить новую» позволяет не превращать каждое событие в массовую загрузку всего приложения. Перечитывают данные активные потребители, которым они действительно нужны.

## Live-обновления: от ручного SQL до актуального списка

### Почему событие начинается в базе

Если уведомлять браузеры только внутри Java-метода изменения студента, ручной SQL обойдет этот метод. Данные в таблице поменяются, а приложения ничего не узнают. Поэтому в проекте уведомление начинается ниже — в PostgreSQL. Миграция [V4__notify_student_changes.sql](backend/src/main/resources/db/migration/V4__notify_student_changes.sql) создает триггер после INSERT, UPDATE и DELETE для каждой строки.

Триггер вызывает `pg_notify` в канале `student_changes` и передает ID. Для удаления используется `OLD.id`, поскольку новой строки уже нет; для вставки и обновления — `NEW.id`. После завершения транзакции слушатели получают уведомление. Если транзакция откатывается, ее NOTIFY не должен сообщать браузеру о несуществующем подтвержденном изменении. Это свойство описано в [документации PostgreSQL](https://www.postgresql.org/docs/current/sql-notify.html).

Java-класс [StudentEvents](backend/src/main/java/ru/itmo/students/service/StudentEvents.java) держит отдельное соединение, выполняет LISTEN и принимает уведомления. Далее рассылает браузерам событие `students-changed`. Получается цепочка: изменение таблицы, commit, уведомление PostgreSQL, Java-слушатель, событие браузеру, очистка кеша, новое чтение API. Ручной SQL и запрос сайта сходятся на изменении одной таблицы, поэтому оба пути способны вызвать обновление.

Минтус, по контексту проекта, требовал обновления списка и открытой карточки, включая изменения через SQL. Конкретно PostgreSQL LISTEN/NOTIFY и SSE он не назначал обязательными технологиями. Это выбранное решение условия, и на защите его следует объяснять через задачу, которую оно решает.

### Зачем уведомлять, а затем перечитывать

SSE, Server-Sent Events, передает события от сервера браузеру через длительное HTTP-соединение. В проекте браузер создает `EventSource`, а Java пишет события через `SseEmitter`. Это подходит для уведомлений «данные изменились»: обратные изменения браузер по-прежнему отправляет обычными HTTP-запросами. Двусторонний WebSocket ради одного такого направления не обязателен. Базовый протокол EventSource определен в [HTML Standard](https://html.spec.whatwg.org/multipage/server-sent-events.html).

Сообщение содержит ID, а не готовую версию всей таблицы. Браузер использует его как повод перечитать источник. Список перечитывается при студенческом изменении; карточка может отфильтровать уведомление по своему ID. Такой подход не требует восстанавливать сортировку, фильтры и пагинацию из отдельных низкоуровневых событий. Java API снова возвращает нормальный результат по текущим параметрам.

SSE-событие не является надежной базой данных и не доказывает, что все прошлые события получены. Соединение может оборваться. Поэтому предусмотрено `ready`: после подключения браузер тоже проверяет данные, а после восстановления PostgreSQL-соединения Java рассылает такой сигнал снова. Это сверка с источником после возможного пропуска. При ошибке SSE клиент закрывает соединение, проверяет `/me` через общий HTTP-клиент и пытается подключиться заново.

Между commit и новым отображением все равно проходит время. Требуются доставка уведомления, обработка Java, сеть и повторное чтение. Следовательно, live-обновление не превращает все браузеры в одно мгновенно синхронное состояние. Даже при правильной реализации две вкладки могут короткое время показывать разные версии. Здесь приемлемое поведение — автоматически приблизить открытые чтения к актуальному состоянию после изменения и восстановить их после переподключения, а не обещать нулевую задержку.

Отсюда видно отличие уведомления об изменении от ответа на сохранение. Ответ POST или PUT нужен инициатору, чтобы узнать результат именно своей операции. Событие SSE получают и другие подписчики, которым может потребоваться перечитать список. Эти сообщения не заменяют друг друга: успешное уведомление не должно заставлять форму считать свой неуспешный запрос сохранением, а HTTP-ответ одному браузеру не сообщает автоматически о правке всем остальным.

Форму редактирования чужое изменение не заполняет поверх введенного текста. Свежая карточка и пользовательский черновик решают разные задачи. Здесь также нет optimistic locking, который запрещал бы двум администраторам последовательно перезаписать запись без проверки ее версии. Live-обновление чтения нельзя выдавать за полноценное разрешение конфликтов редактирования.

Возможное уточнение на защите: если уведомление потерялось, гарантирован ли каждый промежуточный вариант студента? Нет. Цель реализации — получить актуальное состояние, а не показать полный журнал изменений. Повторное чтение после `ready` восстанавливает итоговое состояние, но не историю всех событий.

### RxJS: ожидание ввода и отказ от старой работы

Пока пользователь печатает фильтр, отправлять запрос после каждого символа невыгодно. Нужна пауза после последнего изменения. В lab5 [studentSearch.js](frontend/app/utils/studentSearch.js) реализует ее через `timer(delay)` внутри `switchMap`. Новое изменение отменяет подписку на предыдущую ветку, включая прежнее ожидание таймера. Для фильтров страница передает 3000 миллисекунд; для страницы списка или другого немедленного чтения — ноль.

Это поведение соответствует идее debounce, но оператора `debounceTime` в текущей реализации нет. Нельзя на защите искать выдуманную строку с ним. `switchMap` переключает подписку на новую внутреннюю последовательность и перестает передавать результаты прежней. Его действие видно в [исходнике RxJS 7.8.2](https://github.com/ReactiveX/rxjs/blob/7.8.2/src/internal/operators/switchMap.ts). Когда внутренний Observable освобождается, его функция завершения вызывает `AbortController.abort()`, поэтому старое HTTP-ожидание действительно получает сигнал отмены.

Отмена подписки и отмена серверной операции различаются. Promise сам по себе не обладает универсальным методом остановки, а `abort` не откатывает уже выполненный SQL. Здесь запрос поиска является чтением; задача отмены — перестать ждать и применять неактуальный результат. Для изменения данных требовалась бы отдельная проверка того, успел ли сервер принять операцию.

События live-обновления приходят в отдельный `refresh`, который перечитывает текущие параметры без новой трехсекундной паузы после завершения ожидания фильтра. Ошибка превращается через `catchError` в значение для интерфейса, поэтому один сетевой отказ не уничтожает навсегда весь поток будущих поисков. `startWith` сообщает о состоянии загрузки до появления ответа. Это еще одна причина понимать Observable как последовательность значений, а не как просто необычный Promise.

Возможное уточнение на защите: почему нельзя просто принять тот запрос, который завершился последним? Последним способен завершиться самый старый медленный запрос. Если после фильтра «А» пользователь выбрал «Б», порядок ответов может оказаться обратным порядку намерений. `switchMap` сохраняет актуальность относительно последнего изменения входного потока, а не относительно скорости сервера. Аналогичная проблема возникает у карточки: более новая загрузка отменяет прежнюю, чтобы старое завершение не перезаписало актуальную запись.

## Сессия при SSR: cookies, токены и изоляция пользователей

### Где находится окончательная проверка

Сервер Nuxt умеет получить профиль и подготовить страницу, но не становится владельцем проверки пароля или выдачи JWT. Эти решения остаются у Java. В [TokenService](backend/src/main/java/ru/itmo/students/service/TokenService.java) access является подписанным JWT, а refresh — случайной UUID-строкой. В базе хранится хеш refresh. Не каждый токен обязан быть JWT: название описывает назначение, а формат выбирается отдельно.

Access подтверждает возможность обращения к API в течение ограниченного срока. Подпись позволяет обнаружить подмену содержимого, но не превращает JWT в зашифрованный секретный контейнер. Проверяются подпись, срок и ожидаемый issuer. Refresh нужен для получения следующей пары без повторного ввода пароля и проверяется через серверную запись. При ротации прежний refresh потребляется, а вместо него выдается новый.

Удаление пригодного refresh через `DELETE ... RETURNING` не дает двум конкурирующим обменам независимо получить одну и ту же запись как еще действующую. Но одновременно объясняет необходимость согласования: два легитимных запроса могли прибыть с одной старой cookie. Клиент объединяет refresh внутри своего экземпляра, а Nitro согласует связанные серверные auth-запросы. Это не перенос авторизации в Nuxt: решение о действительности самого токена остается у Java.

Возможное уточнение на защите: зачем серверу запись refresh, если JWT stateless? Stateless относится к проверке access в выбранной модели. Долговременный refresh и возможность его отзыва реализованы через состояние базы. Смешанная модель не противоречива: разные токены решают разные задачи.

### Что дают атрибуты cookie

Java возвращает auth-токены через Set-Cookie, а не JSON. Браузер сохраняет их и прикладывает к подходящим запросам. `HttpOnly` закрывает чтение значения через обычный JavaScript, но не мешает браузеру отправить cookie. Он не защищает от любого XSS: вредоносный код все еще может пытаться выполнять действия в открытом приложении. `Secure` ограничивает отправку защищенным соединением; в проекте флаг зависит от конфигурации среды. `Path=/` делает auth-cookies подходящими и для прямого запроса `/profile`. Эти свойства относятся к доставке cookie, а не назначают пользователю роль. Основа механизма описана в [RFC 6265](https://www.rfc-editor.org/rfc/rfc6265.html).

`SameSite=Lax` ограничивает отправку в некоторых межсайтовых сценариях, но не означает «принимать только свой JavaScript». Правила атрибута приведены в [документации Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie#samesitesamesite-value). Важно также различать site и origin: разные порты одного хоста не создают независимые cookie-хранилища только за счет порта. Поэтому у lab5 отдельные имена `lab5AccessToken` и `lab5RefreshToken`. Нельзя рассчитывать, что другой порт автоматически отделит ее от соседней лабораторной.

### Почему JWT в cookie не отменяет CSRF

Автоматическая отправка cookies удобна для входа и одновременно создает риск CSRF: чужая страница пытается заставить браузер выполнить запрос с уже имеющимися учетными данными. Само наличие действительного access в запросе не показывает, что пользователь хотел именно это действие. Отсюда отдельная проверка CSRF для изменяющих операций.

Клиент получает через `/api/auth/csrf` JSON с именем заголовка и значением токена, затем помещает значение в специальный заголовок. Cookie-часть CSRF передает браузер. Поэтому HttpOnly у CSRF-cookie не мешает текущему протоколу: JavaScript берет необходимое значение из ответа, а не читает cookie напрямую. Стандартный обработчик Spring умеет маскировать передаваемое значение; сравнивать его строкой с сырым содержимым cookie как единственный критерий правильности нельзя. Механизм описан в [Spring Security CSRF](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html).

`permitAll` для регистрации или входа не отключает CSRF-фильтр. И `{ auth: false }` в клиенте означает только отказ от автоматического refresh и уведомления об истечении для данного обращения. Оно не отменяет CSRF и не делает запрос анонимным. Для QUERY текущий код тоже получает CSRF: клиент исключает из этой процедуры GET, HEAD и OPTIONS, а QUERY не является исключением ни у клиента, ни у Java.

### Почему SSR требует явной передачи заголовков

Когда браузер непосредственно вызывает API, подходящие cookies сопровождают запрос по правилам браузера. При SSR обращение к Java выполняет Node-процесс. Его обычный серверный fetch не является браузерным хранилищем конкретного посетителя и не получает cookie автоматически только потому, что вызван во время рендера.

Поэтому [01.session.js](frontend/app/plugins/01.session.js) читает Cookie исходного HTTP-запроса в отдельную карту, передает ее Java и обрабатывает ответные Set-Cookie. Новые значения нужны сразу в двух местах: в следующих запросах текущего SSR и в заголовках ответа браузеру. Иначе сервер способен построить страницу с новой сессией, а браузер останется со старой, либо наоборот.

Это объясняет, почему `Path=/` важен именно при прямом открытии. Если refresh-cookie приходила бы только на узкий auth-путь, первоначальный запрос `/profile` мог бы ее вообще не содержать. Nuxt не сумеет восстановить вход значением, которого не получил. Также нельзя переслать всем пользователям одну общую серверную карту cookies: она относится к конкретному запросу.

При этом на сервере действительно существует общая Map в [server/utils/auth.js](frontend/server/utils/auth.js). Почему это допустимо, если общий `currentUser` опасен? Map решает другую задачу: сопоставляет связанные auth-операции по хешу адреса Java и конкретного refresh. Она не объявляет одного посетителя текущим для всего процесса и не заменяет проверку токена. У каждого входящего запроса сохраняется собственный `authOwner`, а связанные операции могут разделять очередь. Изоляция не означает запрет любой общей структуры; она требует точно определить, какие данные объединяются и по какому основанию.

Еще одна граница — несколько процессов Nuxt. Обычная Map одного процесса не становится автоматически общей для другого процесса или другого контейнера. Текущая реализация рассчитана на предусмотренный проектом серверный процесс, а не на произвольное горизонтальное масштабирование без дополнительных решений. На защите достаточно честно назвать это ограничение, не предлагая сразу распределенный кеш, очередь сообщений и новые слои, которых в лабораторной нет.

### Один повтор, маленький store и несколько вкладок

В [api.js](frontend/app/utils/api.js) защищенный запрос после подходящего `401` допускает один цикл восстановления и один повтор исходного обращения. Это ограниченная ветка, а не рекурсия «повторять до успеха». `403` с недостаточной ролью не исправляется выпуском нового access с той же ролью; `503` не доказывает исчезновение пользователя. Только окончательный актуальный `401` при остальных выполненных условиях приводит к реакции на истечение.

Внутри общего refresh перед обновлением снова читается `/me`. Пока текущая операция ждала блокировку, другая вкладка могла уже получить новые cookies. Если профиль теперь читается, повторно потреблять refresh не требуется. Есть и дополнительная проверка `/me` после `401` самого refresh: она позволяет обнаружить уже изменившееся состояние. Эта последовательность не бесконечна; исходный `request` по-прежнему имеет одну явно ограниченную попытку восстановления.

Смена cookies и получение профиля — разные этапы. Успешный POST входа дает `204`, поэтому после него менеджер сбрасывает `checked` и отдельно определяет пользователя. Если последующее чтение столкнулось с `503`, неправильным становится не пароль, а завершение загрузки. Если получен окончательный `401`, менеджер может очистить сессию и вернуть `null` без исключения. Поэтому само успешное ожидание `loginUser()` не следует объявлять доказательством заполненного пользователя; защищенный маршрут все равно читает актуальное состояние.

У выхода порядок обратный преждевременному оптимизму: сначала ожидается подтвержденный HTTP-результат, затем очищаются пользователь и зависимые данные. Ошибка сохраняет локальный профиль, но не доказывает сохранность серверной сессии. При обрыве связи сервер мог уже обработать logout. Следующее обращение определит фактическое состояние. Ожидание `logoutPromise` перед новым `loadUser` предотвращает чтение промежуточного состояния во время выполняющегося выхода.

Pinia хранит `user`, `checked` и getter роли. `checked` означает, что приложение приняло результат проверки; флаг не доказывает бессрочную действительность серверной сессии. Сценарии находятся в `session.js`, транспорт — в `api.js`. Такое разделение выбрано для объяснимости этой работы, а не потому, что Pinia запрещает асинхронные actions. На сервере store и сервисы относятся к экземпляру текущего приложения; обычная общая переменная `currentUser` на уровне модуля могла бы смешать посетителей.

Версии в менеджере не позволяют запоздавшему `/me` перезаписать нового пользователя или очистить его старой ошибкой. В браузере поддерживаемый Web Locks упорядочивает участвующие login, logout и refresh. Между вкладками cookies общие, но Pinia разная. Поэтому подтвержденная смена авторизации записывает в localStorage только отметку времени со случайной добавкой. Соседняя вкладка при подходящей отметке перечитывает документ и получает актуальную сессию. Токенов и профиля в отметке нет.

Блокировка и версии не взаимозаменяемы. Блокировка удерживает порядок участвующих операций, пока они выполняются; версия проверяет актуальность результата после ожидания. Счетчик сам по себе не останавливает чужой HTTP-запрос и не блокирует сервер. И наоборот, последовательные POST не гарантируют, что старый GET профиля не завершится позже. Именно поэтому рядом оказываются оба механизма. Поведение Web Locks описано в [спецификации W3C](https://w3c.github.io/web-locks/); если API недоступен, адаптер просто вызывает действие без этой браузерной очереди.

Если localStorage недоступен, вход не должен падать, однако той же автоматической синхронизации уже нельзя обещать. Успешный выход отзывает соответствующий refresh и очищает cookies, но не мгновенно уничтожает скопированный ранее access JWT: отдельного списка отзыва access в проекте нет. Эти границы полезно проговорить прямо. Уверенный ответ на защите — точное описание существующего механизма, а не обещание универсальной защиты от любых гонок и атак.

## Vue: уточнения, на которых легко потерять объяснение Nuxt

### Реактивность относится к значениям, которые действительно отслеживаются

Nuxt использует Vue, поэтому SSR не отменяет вопросы про `ref`, `reactive` и обновление компонента. В лекции 9 это связь между состоянием и интерфейсом: меняются данные, а Vue определяет, какое отображение зависит от них. Программа не ищет каждую ячейку таблицы вручную.

`ref` дает объект с реактивным свойством `.value`. В JavaScript чтение `busy.value` и последующее изменение проходят через этот объект; в шаблоне верхнеуровневый ref обычно распаковывается автоматически. `reactive` возвращает Proxy для объекта: перехватываются обращения к его свойствам. Это разные формы доступа к отслеживаемому состоянию, а не два способа сохранить данные на сервере.

В формах lab5 используется `reactive({ username: '', password: '' })`. Если отдельно записать `const username = form.username`, получится обычное текущее значение строки. Оно не становится связанной переменной, которая сама меняется при следующем вводе в `form.username`. Поэтому в обработчике читается само свойство формы. Аналогично деструктуризация свойств store может потерять связь со значениями; для реактивного извлечения состояния Pinia существует `storeToRefs`. В проекте чаще просто читают `auth.user` и `auth.isAdmin`.

**Возможное уточнение на защите: почему обычная переменная меняется в консоли, но экран остается прежним?** Присваивание JavaScript-переменной и регистрация реактивной зависимости — разные операции. Новое значение может существовать, но Vue не получил через `ref` или Proxy сигнал, который связывает его изменение с обновлением компонента. Не следует объяснять это «JavaScript не заметил присваивание»: он выполнил его нормально.

### Вычислить значение и выполнить действие — разные задачи

`computed` нужен для значения, получаемого из других реактивных данных. В списке количество страниц зависит от общего количества записей и размера страницы. Getter не должен заодно отправлять запрос, очищать store или менять фильтр: чтение значения тогда неожиданно станет действием. Результат computed кешируется с учетом зависимостей; пересчет при необходимости связан с их изменением, а не с каждым чтением как у обычного вызова функции.

`watch` нужен для реакции с побочным действием. Например, в профиле наблюдение за `auth.user` инициирует переход на вход, если пользователь исчез. Оно не вычисляет новый профиль и не заменяет проверку Java. Источник указывается явно: `watch(() => auth.user, ...)` следит за результатом getter, а не за любой переменной, случайно упомянутой в callback.

`watchEffect` сам отслеживает реактивные чтения синхронной части своего выполнения. Для асинхронной функции особенно важно слово «синхронной»: чтения после первого `await` не становятся автоматически такими же отслеживаемыми зависимостями. В lab5 нет необходимости заменять понятный `watch` этим API; знать различие полезно, чтобы объяснить выбор явного источника. Подробности поведения определены [Vue](https://vuejs.org/guide/essentials/watchers.html).

**Возможное уточнение на защите: зачем computed, если можно пересчитывать значение в watch?** Для чистой зависимости watch заставит отдельно хранить исходное и производное значения и согласовывать их вручную. Computed описывает саму зависимость. Watch оправдан, когда требуется действие: запрос, переход, взаимодействие с внешним API, а не еще одна копия вычисляемого числа.

### Изменение состояния и готовность DOM не совпадают по времени

После изменения ref Vue группирует обновления DOM. Значение JavaScript уже новое, а чтение элемента сразу следующей строкой еще может увидеть прежнее отображение. `nextTick()` позволяет дождаться очередного применения обновлений Vue. Он не ожидает произвольный HTTP-запрос и не обещает завершение всей работы браузера, картинок и сервера. У каждого ожидания свой предмет.

При SSR DOM браузера вообще отсутствует. `onMounted` нужен для действий после клиентского монтирования, например подписки открытого списка на дальнейшие изменения. Первоначальные данные для серверного HTML поэтому получают не только в `onMounted`. Иначе сервер не сможет включить их в документ, даже если включено `ssr: true`.

Очистка тоже зависит от среды. Подписка, обработчик или запрос должны перестать обслуживать закрытую страницу. В браузере для этого есть отмена и lifecycle-хуки. Но нельзя поставить бесконечный таймер в общем серверном коде компонента и надеяться, что его обязательно уберет обычный браузерный `onUnmounted`. Сервер не проходит клиентский жизненный цикл монтирования и удаления DOM. Это одна из причин отдельно определять время жизни каждого ресурса.

### Props, события и key объясняют поведение таблицы

[StudentTable.vue](frontend/app/components/StudentTable.vue) получает `students`, `isAdmin` и `busy` через props. Решение удалить запись остается у страницы: таблица сообщает о действии через `$emit('delete', student)`. Событие компонента — сообщение родителю, а не встроенный HTTP-запрос. `emit` также не возвращает потомку результат асинхронного удаления как обычный вызов обещающей его функции. Поэтому готовность операции отражается через состояние, переданное обратно в props.

В списке используется `:key="student.id"`. Key помогает Vue сопоставить экземпляры элементов при изменении порядка или удалении. Индекс массива описывает место, а ID — запись: после удаления первого студента второй меняет индекс, но не свою личность. Это важно для связанного состояния компонентов и полей ввода. При этом key не является правом доступа и сам по себе не ключ кеша API: одинаковое слово обозначает разные механизмы.

`v-if="isAdmin"` определяет наличие административных элементов в дереве интерфейса. `:disabled="busy"` временно запрещает взаимодействие с элементом. Это полезные ограничения поведения страницы, но не серверная авторизация. HTTP-запрос можно отправить без таблицы, и тогда сработают правила Java. Так вопрос про одну директиву возвращается к общей границе ответственности всей лабораторной.

## Docker: почему серверный frontend требует другой доставки

### Образ содержит программу, контейнер исполняет ее

Docker-образ — подготовленный набор слоев файловой системы и настроек процесса. Контейнер — конкретный экземпляр его выполнения с собственными процессами и изменяемым слоем. Один образ может использоваться несколькими контейнерами, а остановка процесса не превращает образ обратно в исходный проект. Данные PostgreSQL должны переживать замену контейнера, поэтому они вынесены в отдельный том.

Главное изменение lab5 связано с SSR. Обычную клиентскую сборку Vue можно раздавать как статические файлы, но текущая lab5 исполняет Nuxt/Nitro на Node: для нового запроса нужно прочитать cookies, получить пользователя и построить HTML. Поэтому один Nginx со статическими файлами не выполняет роль SSR-сервера. В [frontend/Dockerfile](frontend/Dockerfile) финальное окружение содержит Node и результат `.output`, а не только папку HTML/CSS/JS.

**Возможное уточнение на защите: Nuxt всегда требует Node?** Нет, существуют другие варианты развертывания и статический prerender. Ответ про Node относится к выбранной конфигурации `node-server` и серверным функциям именно lab5. Статический сайт с заранее готовым HTML не сможет тем же способом строить персональный HTML по cookies каждого нового посетителя.

### Многоэтапная сборка отделяет инструменты от результата

Во frontend первая стадия устанавливает зависимости и получает серверный результат Nuxt. Следующая получает `.output` и среду Node для исполнения. В backend первая стадия создает Spring Boot JAR с инструментами Gradle и JDK, следующая содержит JRE и готовый JAR. Компилятор нужен при получении артефакта, но не обязан присутствовать рядом с готовым Java-приложением. Так уменьшается набор файлов и инструментов в финальном образе.

Это назначение [многоэтапной сборки](https://docs.docker.com/build/building/multi-stage/), а не дополнительный слой бизнес-логики. Также стоит различать кеш Docker при подготовке образа и кеш данных приложения. Порядок `COPY` файлов зависимостей перед остальным frontend-кодом позволяет повторно использовать ранее полученный слой, если соответствующие входные данные не изменились. Это не сохраняет список студентов и не задает его свежесть.

Lockfile фиксирует разрешенные версии пакетов и помогает получать воспроизводимый набор зависимостей. Он не гарантирует абсолютную идентичность любого будущего окружения: еще имеют значение базовый образ, архитектура и внешние условия. Для объяснения лабораторной достаточно назвать, какие входы контролируются и зачем не пересчитывать версии произвольно при каждой подготовке.

### Сеть, готовность и хранение данных решают разные задачи

В [docker-compose.yml](docker-compose.yml) четыре сервиса: PostgreSQL, Java-backend, Nuxt-frontend и Nginx. Между контейнерами используются имена сервисов, например `http://backend:8080`. Адрес `localhost` внутри frontend-контейнера означает этот же контейнер, а не Java в соседнем. Браузер, напротив, знает внешний адрес сайта и относительный `/api`; внутреннее имя `backend` ему не требуется.

Nginx направляет запросы в подходящий сервис. Он не проверяет пароль вместо Spring и не превращает любой проксируемый ответ в SSR. Серверный HTML формирует Nuxt; API студентов обслуживает Java; отдельные auth-адреса согласует Nitro. Единственный внешний адрес упрощает передачу cookies и взаимодействие браузера, но не отменяет обязанности каждого участника.

`depends_on` с условием `service_healthy` связывает готовность зависимостей с переходом к зависимому сервису. Сам по себе существующий контейнер еще не означает, что приложение внутри готово отвечать. При этом healthcheck — ограниченная проверка, а не доказательство правильности всего сайта: ответ на `/login` не проверяет все комбинации ролей, SSR и ручного SQL. Позднейший отказ зависимости также остается ошибкой, которую приложение обязано обрабатывать.

Том `postgres_data` хранит файлы базы отдельно от изменяемого слоя контейнера. Сохранность тома не означает автоматическое резервное копирование. А `.env` передает настройки и секреты окружению серверных сервисов; он не должен попадать в браузерный payload или Git. Публичная конфигурация Nuxt и серверная конфигурация имеют разное назначение. В lab5 внутренний `backendUrl` не помещен в `runtimeConfig.public`.

## Скорость страницы: что именно улучшил выбранный механизм

В конце лекции 10, на слайдах 68–69, производительность разделена на наблюдаемые свойства. **LCP** оценивает время появления крупнейшего подходящего элемента содержимого. **INP** описывает задержку от взаимодействия до следующей отрисовки: сюда входят ожидание занятого главного потока, выполнение обработчиков и подготовка показа. Это не время получения полного HTTP-ответа. **CLS** оценивает неожиданные сдвиги макета. Одно число «страница стала быстрее» не объясняет, какой из этих эффектов изменился.

SSR может раньше дать содержимое, но медленный запрос Java задержит серверный ответ. **TTFB** — время до первых байтов ответа — поэтому способно увеличиться. После появления HTML большой клиентский JavaScript еще может задерживать обработку действий. Смена CSR на SSR сама по себе не устраняет длинную задачу на главном потоке и не резервирует место под изображение, которое позднее сдвинет текст.

**Возможное уточнение на защите: почему пользователь уже видит страницу, но кнопка еще не работает?** Видимость серверного HTML и завершение клиентской гидратации — разные моменты. Нужно выяснить, что именно задерживает интерактивность: загрузка кода, его выполнение или другой ресурс. Дополнительный SSR не делает клиентские обработчики готовыми раньше собственного исполнения.

Измерение должно соответствовать предполагаемой причине. При последовательных независимых API-запросах полезно убрать лишние ожидания. При тяжелом клиентском обработчике — уменьшить работу на главном потоке. При сдвиге макета — стабилизировать размеры и структуру. Prefetch может уменьшить ожидание после клика, но потратить трафик на страницу, которую человек не откроет. Кеш может сократить обращения, но требует корректного правила свежести. Поэтому обоснование оптимизации включает не только выигрыш, но и то, какой ценой он получен.

## Общий HTTP-клиент: объяснить request, а не спрятаться за fetch

По сообщениям Карима, функция `request()` уже становилась предметом уточнения на защите предыдущей лабораторной. Поэтому ее смысл полезно уметь изложить как последовательность действий. Это не повод запоминать весь файл наизусть: нужно понимать входные данные, состояние, возврат и отказ.

Студенческий сервис вызывает общий клиент с методом, адресом, необязательным телом и параметрами обращения. Например, DELETE нуждается в ID в адресе, но не обязательно в JSON-теле; QUERY передает условия выборки телом. [api.js](frontend/app/utils/api.js) при наличии данных добавляет `Content-Type: application/json` и преобразует объект через `JSON.stringify`. Для методов вне клиентского списка исключений он предварительно получает CSRF. Затем адаптер выполняет запрос в нужной среде: браузерный fetch или серверное обращение с перенесенными cookies.

Сам HTTP-ответ еще не является объектом студента. У него есть статус, заголовки и тело, которое предстоит прочитать. `request` сначала может обработать подходящий `401`, а затем передает итоговый ответ в `readResponse`. Успех без тела дает `null`. Успешный JSON становится данными вызывающего кода. Неуспешный JSON превращается в Error со статусом, сообщением и при наличии полевыми ошибками. Если сервер вернул HTML вместо ожидаемого JSON, это тоже отдельная ошибка разбора ответа, а не корректный объект списка.

Возможное уточнение на защите: **«Зачем эта обертка, если можно в каждом компоненте написать fetch?»** Можно, но тогда каждый экран отдельно повторит сериализацию, чтение ответа, CSRF, обработку пустого успеха и восстановление после `401`. Общий клиент собирает одинаковые технические правила. Предметный сервис выбирает, какие данные нужны, а компонент решает, как отобразить результат. При этом дополнительная обертка оправдана именно повторяющейся работой; она не требует универсальной архитектуры из множества базовых классов.

QUERY в лабораторной сохраняет прежний контракт расширенного поиска. Его выбор в [students.js](frontend/app/utils/students.js) связан с количеством фильтров и длиной представления в URL. Это проектное правило, а не универсальный стандарт «после четвертого поля всегда меняй метод». Точно так же HTTP-клиент не решает, какой студент попадет в выборку: проверка и выполнение условий остаются у Java.

При объяснении деталей Nuxt использована документация ветки 4.x; связанные официальные источники указаны рядом с соответствующими механизмами. Для Vue дополнительно полезны страницы [реактивности](https://vuejs.org/guide/extras/reactivity-in-depth.html) и [computed](https://vuejs.org/guide/essentials/computed.html), для метрик — [Web Vitals](https://web.dev/articles/vitals).

Предположения о вероятных уточнениях преподавателя основаны на сообщениях Карима о прежних замечаниях, а не на отдельном опубликованном списке Минтуса. Они помогают выделить трудные связи между понятиями, но не исключают остальные вопросы письменной программы.
